# 框架缺口：技法层与运行时

来源：给两个玩家 agent 补动作类技法（`train_unit` / `build_structure` / `place_ready_building` / `focus_fire` / `guard_area`）时逐条撞出来的。
范围：`src/ra2agent/tactics/` 与 `micro.py` / `command.py` / `autopilot.py` 之间的接口。
状态：缺口二、七已由 `2e61dce` 修复；缺口三（条件问错对象）已在技法侧绕过；`_advance` 崩溃已修（见下）；缺口一、四、五、六留待下一轮。

## 已修：缺口二——适用条件拿不到调用参数（`2e61dce`）

`missing_conditions` 现在收参数，受理点、`_invoke`、`admit` 各传手上已有的那一份。
`can_afford`、`cell_explored`、`cell_unknown` 因此真的会判。
两条仍然成立的限制（已写进 `conditions.py` 与 skill）：

- **卡片筛选拿不到参数**：参数型条件不会让卡片消失，只在 `call` 受理与技法真跑时生效；
- 条件在两种 `subject` 下各判一次，能用 `observation` 判的就别碰 `subject`。

**一处文档与实现不一致**：`conditions.py` 的契约二与 `core.py` 的 `missing_conditions` 文档都说「受理点在 `check_params` 之前就判条件，故探针里的 `params` 是原始请求、默认值尚未补上」；而 `command.py:638` 一带实际是**先 `check_params`（补默认值）再判条件**，传进去的是补好的那一份。skill 说的与代码一致，这两处注释该跟着改。

## 已修：缺口七——任务失败原因不进 `status`（`2e61dce`）

`reason` 现在经 `_settle` 进 `completed` 记录，`status` 的「新结果」渲染一行「原因：……」；成功的结果不带这行。`ERROR_REASONS` 补了 `no_completed_object`。
随之确定的用法：**常规失败不要再走 `Wake`**（那是每拍可算的事实），`Wake` 只留给只有模型能决定的事。

## 已修：`_advance` 遇到没有 `units` 的意图就崩（本批附带）

**现象**：`Produce` / `Place` / `Sell` 三种意图**一执行成功就抛 `AttributeError`，整拍崩掉**。

**证据**：`micro.py:383` 原先写 `covered = set(intent.units)`，而这三个意图类的字段是 `type_pointer` / `building` / `buildings`，**没有 `units`**（见 `intents.py`）。`_advance` 只在 `executor.execute` 成功之后才跑，所以命令是真的会发出去、然后崩在记账这一步。`_order` 只接 `TacticDenied`/`TacticError`，`_dispatch` 只接 `Ra2Error` 那几类，`AttributeError` 会一路穿出 `tick()`。

**影响**：整套生产链此前根本没跑通过——没有技法产出 `Produce`，所以这个分支从未被执行到。「补了技法」与「跑得通」是两件事，这条是典型。

**修法**：无 `units` 的意图退回信封的 `scope.objects`，也就是本次 `call` 点名的单位；这也正是 else 分支「命令生效即算到位」想做的事——把这次点名的单位交还出去。

**验收**：`tests/test_command.py::TestActionTacticsThroughCall` 三条走真实的 `Commander.call` + `tick()`：`train_unit` 受理后真的下发 `Produce`、钱不够时在受理点被 `can_afford` 拒、`place_ready_building` 在 `UnitPool`（受理）与 `Squad`（运行）两种 subject 下都成立。

## 未修：缺口一——空单位调用被拒，阵营级动作没有入口

**现象**：`call` 必须点名至少一个单位；造建筑、造兵、变卖这类不涉及任何对象的动作没有干净的入口。

**证据**：`command.py:666` 的 `_check_units` 对空名单直接返回「没有给出单位」。自动触发那条路不需要单位，但**禁止必填参数**（`core.py:381`），所以 `train_unit(type="MTNK")` 也做不成脉冲。

**注意**：这条限制只检查「名单非空 + id 属于己方」，**不检查它是不是工厂**。它看的是格式，不是能力。

**建议**：`TacticInfo` 加一个「不涉及单位」的标记（如 `unitless=True`），`_check_units` 与 `MicroLayer.assign` 对这类技法放行空 scope。`ctx.intent` 已有 `Scope.empty()` 的分支（`core.py:273`），不必新增机制。

**验证**：注册一条 `unitless` 技法，空 `units` 能受理、能跑、能结算；非 `unitless` 技法仍拒空名单。

## 未修：缺口三——同一条件在受理与运行时问的对象不同（技法侧已绕过）

**现象**：条件在受理时为真、通过；技法真跑起来时为假，任务卡在「等待条件」且永不推进。

**证据**：受理时问的是 `UnitPool`（`command.py:638` 一带，它扫局面里所有己方对象），运行时问的是 `Squad`（`micro.py:300` 的 `_order` 把 `subject=squad` 传给 `registry.run`）。
`has_pending_building` 原先只认 `UnitPool.pending()`，于是 `getattr(subject, "pending", None)` 在运行时为 `None` → 假 → `TacticDenied` → 记一条 `squad_waiting` 什么都不做。
这个 bug 只有在技法**被注册并真的调用一次**之后才会暴露。

**已做的处置**：`has_pending_building` 改成只看 `observation`（不碰 `subject`），两个阶段同一个数据源。

**建议**：把「条件会拿到哪种 subject」的契约写进 `conditions.py` 顶部（`2e61dce` 已写）**并让新技法验收强制走一次 `Commander.call`**（skill 已要求）——这类问题只在那条路上暴露。

## 未修：缺口四——任务没有「空转」与「持续运行」的表达

**现象**：技法返回空元组（"这一拍没事做"）时任务不会结算，单位被这条任务一直占着；反过来，想让任务长期活着（持续防守）也只能靠这个副作用。

**证据**：`micro.py:269` 的 `_settle` 只看每个单位的状态，全部落到 `ARRIVED/LOST/FAILED` 才结算。
`_needs_orders`（`micro.py:396` 一带）在单位是 `MOVING` 且无目标时为真，所以"不下令"的单位每拍都让任务继续存在。
`Autopilot._pulse` **已经有** `idle` 概念（`autopilot.py:92`：意图为空时记 `record["idle"] = True` 且不报给模型）——脉冲路径有，编队路径没有。

**歧义**：空元组现在同时表示「这拍没活干」和「我这辈子干完了」，这是加标记之前要解开的结。

**建议**：三种需求分开表达：
其一，`TacticInfo` 加 `continuous=True`——不按单位状态结算，每拍都调，直到 TTL / `cancel` / 失败；`guard_area` 这类用它。
其二，非 continuous 的技法"连续 N 拍无产出"自动结算，避免占位。
其三，一个「到此为止、但不必再下发命令」的收尾通道。现在能结算的只有两条路：**一条成功的引擎命令**（`_advance` 只在 `executor.execute` 没抛异常后才跑）、或 TTL / `cancel`。技法诊断出"这单根本不该下"时，想干净收尾反而没有办法。

## 未修：缺口五——一条任务走不完一条路径

**现象**：技法里存下一串航点、想逐段下发，做不到——第二段开始技法不会被再调用。

**证据**：`micro.py:396` 的 `_needs_orders`：单位一旦被下了 `MoveTo`，`goal` 非空、`mode=MOVING`，此后**不再需要下令**，于是 `_order` 不再调技法；直到它到达（`ARRIVED` 属于 `DONE_MODES`，任务随即结算）或卡住（`STUCK`）。
走自动脉冲那条路也不行：`autopilot.py:83` 调 `registry.run` 时**不传 memo**，每拍都是新的空记事本，进度攒不下来。

**影响**：多格侦察、"移动途中遇敌即停"都做不成一条任务，只能每格一次 `call` 让模型盯着。单段移动不受影响。

**建议**：缺口四的 `continuous` 标记即可解锁；若还想让脉冲类技法能累计进度，把 `memo` 也传进 `Autopilot._pulse`。

## 未修：缺口六——自动触发的作用范围是「全池」

**现象**：自动运行的技法（含脉冲）拿到的是**己方全部单位**，无法限定"只作用于这一组"。

**证据**：`command.py:508` 调 `autopilot.run(observation, events, self._pool(observation))`，subject 是全池。

**影响**：一条自动"区域防守"会把模型正在调动、正在进攻的部队一起按在原地。这是本轮把 `guard_area` 做成**只由模型显式 call**的原因。

**现状对策**（skill 已写）：写自动触发技法时自己按 `ctx.subject.object_of(id)` 逐个筛要碰的单位，别假设"只有空闲单位"。

**建议**：命名编组，让自动触发可以声明作用于某个组；或至少声明"只碰当前没有任务在身的单位"。

## 未修（设计取舍，不是缺陷）：合法落点不在观测里

`PlaceQuery` 的结果（`sites`）由指挥层问出来、存在 `StatusReport` 里，技法层看不到。
所以"不给 `cell` 自动放建筑"只能按「围着待放建筑找空地」启发式兜底，不合规由 `Validator.check_place` 拦下——不会放错，但会白跑一趟。
要么接受这个取舍，要么把 `sites` 也放进观测。

## 附：本轮已落地的临时妥协

| 妥协 | 原因 | 缺口修好之后可以怎么简化 |
|---|---|---|
| `train_unit` / `build_structure` 要求 `units` 点名一个厂 | 缺口一 | 改 `unitless`，卡片不再提 units |
| `guard_area` 只由模型调用、没有自动触发，长任务要挂 TTL | 缺口四、六 | 有 `continuous` 与命名编组后可做成自动的 |
| 多格侦察交给模型每格一次 `call` | 缺口五 | `continuous` 之后可写成一条路径技法 |

## 优先级建议

| 顺序 | 改动 | 解决的缺口 | 代价 |
|---|---|---|---|
| 1 | `TacticInfo.unitless` + 两处放行 | 缺口一 | 小 |
| 2 | `TacticInfo.continuous` + 结算规则（含主动收尾与空转） | 缺口四、五 | 中 |
| 3 | 命名编组 | 缺口六（并顺带省掉模型每次重列 id） | 中 |
| 4 | 修 `conditions.py` / `core.py` 里那两处与实现不符的注释 | 文档 | 小 |
