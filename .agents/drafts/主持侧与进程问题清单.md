# 主持侧与进程问题清单

来源：主持一局 1v1 的过程中撞出来的，与技法层无关，属 `game` / `match` / `winfocus` 与主持 agent 的运行环境。
配套：[框架缺口-技法层与运行时](框架缺口-技法层与运行时.md) 管技法层与 `micro`/`command`/`autopilot` 的接口，本文件管进程、启动与作用域。

**状态（后补）**：第六、七条已由 `86a73a2`（玩家面裁剪）修掉——`DEFAULT_PLAYER_DENY` 含 `bash`/`pwsh`/`write`/`edit`/各派生入口/`plugin_manager`，名册派生的 `play_as_*` 自动并入；`read`/`glob`/`grep` 保留，故玩家仍能查 `codex/`。
第一到四条据框架侧说也已修，但本工作区看不到（`git log --all` 里没有对应提交），故保留作背景；动它们之前先确认现状。

## 一、`game start` 只能起一方，整局没有工具入口

**现象**：主持起一局 1v1 只能靠 bash 跑 `python3 tools/start_match.py up`；`game` 工具的四个动作里没有「按名册起全」。

**证据**：带 `--player` 启动的 MCP server 给自己建的是**绑定那一方目录与端口**的 `GameHost`（`mcp.py:569`），`launch()` 就是对一个目录 `Start-Process -ArgumentList '-SPAWN'`（`game.py:172`）。故 `game start` 只能起名册里的第一方，起完也不等对手——而 `-SPAWN` 不等对手，只起一方的后果是它在加载界面干等约 60 秒后判对方掉线。
整局级的操作（按名册起全、隔 `launch_gap`、等每一方 `STAGE_INGAME`、按 PID 停）只存在于 CLI：`match.py:267` 的 `launch()` 用 `-PassThru).Id` 逐方记 PID，`match.py:294` 的 `stop()` 按 PID 杀。

**建议**：加一个绑名册的工具动作（`match up` / `match down` / `match status`），只给主持 agent。这样「起一局对战」才是工具能表达的事，脚本退回纯运维用途。

## 二、`game stop` 按映像名杀，一次杀两个实例

**现象**：任何一方（或主持）调 `game stop`，两个游戏进程一起没。

**证据**：`game.py:186` 是 `taskkill /IM gamemd-spawn-ra2yrcpp.exe /F`——按映像名。两个参与者的可执行文件同名（同一份硬链接）。
CLI 那条路是**按 PID** 杀的，`match.py:294` 的注释里专门写了「只按 PID 杀……按映像名杀会一次杀掉两个」。**知道这件事的那条路绕开了，暴露给模型的那条路踩了坑。**

**建议**：`game stop` 改成 PID 级（复用 `MatchHost.stop()` 的归属逻辑）；或把 `start`/`stop` 从玩家面移走——玩家需要的是「帧在涨吗」，不是「管进程」。

## 三、`focus` 按标题子串找窗口，两个实例同名会串台

**现象**：一方的「抢焦点」可能把**另一方**的窗口置前。

**证据**：`winfocus.py:113` 的 `find_window(substring)` 遍历可见窗口、返回**第一个**标题含子串的；`focus_game()` 用的子串是固定的 `Yuri's Revenge`（`winfocus.py:131`）。两个实例标题完全相同，故没有任何东西把窗口与调用者的实例绑定。
另外 `reset()`（`winfocus.py:148`）是**先 `focus_away()` 再 `focus_game()`**：每次 focus 调用本身就是两次前台切换，中间还把前台丢给随便一个别的窗口。

**建议**：按实例定位——探针知道自己的 PID，用 `GetWindowThreadProcessId` 反查属于自己的句柄；查不到就报错，不猜。

## 四、`game status` 把「前台窗口不是游戏」写成「主循环暂停」

**现象**：`game status` 报「窗口失焦，主循环暂停——用 game focus 抢回焦点」，而帧号同时在涨。

**证据**：`game.py:227` 那行文本来自 `is_game_foreground()`（`winfocus.py:104`）——它只把**当前前台窗口的标题**与 `Yuri's Revenge` 做子串匹配。测的是「前台窗口是不是游戏」，不是「主循环停没停」。
双实例部署装了 cnc-ddraw 的 `noactivateapp`，实测两个游戏窗口都在后台时帧照涨。玩家 agent 因此误判过一次，去调 `game focus`。

**建议**：状态行只报测到的事实（前台窗口是谁 + 帧号推进量），「疑似暂停」只在**帧号确实停住**时才出现并附上依据。

## 五、主持的 bash 看不到任何别的进程（沙箱限制）

**现象**：主持无法观察或重启两个 MCP server、也看不到游戏进程；`ps` 只有自己的 5 个进程。

**证据**：bash 工具跑在 `bwrap --ro-bind / / --dev /dev --unshare-pid --proc /proc ...` 的**私有 PID 命名空间**里。据此我曾误判过「某个后台作业已经不在跑」——那次结论作废。
`start_match.py status` 不受影响：它靠探针端口与 PowerShell 查 PID，不走 `ps`。

**后果**：技法库没有热加载（注册表在 MCP server 连上游戏时构造一次），而主持**没有能力**重启那两个 server；只能靠「重开一局」或「重派玩家」让新代码生效。
另：主持在沙箱里也**写不了**工作目录之外的东西，故任何落在 `/home/youthz/ra2-agent` 之外的运维动作都要人来。

**建议**：不必改沙箱（它是对的），但要把「改技法 → 必须重开一局或重派玩家」写进文档，别让人以为改完就生效。

## 六、玩家面此前是全功能编码 agent（已由另一个会话裁掉）

**记录在案，不重复要求**：玩家 agent 原先是完整 `ra2` preset，手上有 `bash`、`read`/`write`/`edit`、`subagent`、`workflow`、`plugin_manager`，以及 profile 级注册的 `play_as_alpha` / `play_as_beta`，还有 `game start`/`stop`/`focus`。隔离只覆盖 `mcp__ra2__*` 那 5 个名字。
工具裁剪已由另一个会话完成（当前会话不生效，新会话生效）。本文件的第一、二、三条与它不冲突：那三条是**动作本身的作用域**问题，不是玩家面宽窄的问题——即使玩家只剩只读工具，`game stop` 仍然会杀两个实例。

## 七、顺带一条已验证的事实：`play_as_*` 在玩家手里会 fail closed（但理由不对）

**现象**：玩家调 `play_as_beta` 会被拒，但拒绝理由与权限无关。

**证据**：`startPlayerAgent` 唯一的调用者校验是「调用者工具表里还看得见 `mcp__ra2__*`」；玩家那份已被 restrict 摘掉，于是报「看不到 `mcp__ra2__*` 工具，无法证明子 agent 不会继承」并拒绝。整个函数里没有一句问「你是不是主持 agent」。
若玩家面裁剪把这条一起摘掉，问题自然消失；若保留，建议补一条真正的调用者校验。

## 优先级建议

| 顺序 | 改动 | 影响 |
|---|---|---|
| 1 | `game stop` 改 PID 级或从玩家面移走 | 破坏性动作，一次误杀丢两局 |
| 2 | `match up/down/status` 工具（绑名册，只给主持） | 起局不再必须过 bash |
| 3 | `focus` 按实例定位 + 不需要时不动手 | 消除跨实例串台 |
| 4 | `game status` 只报事实、暂停判据看帧号 | 消除一次已发生的误判 |
| 5 | 文档写明「改技法要重开一局」 | 省一轮困惑 |
