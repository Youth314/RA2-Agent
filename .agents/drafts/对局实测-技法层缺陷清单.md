# 对局实测：技法层缺陷清单

> 状态：对局或开发阶段的问题记录；包含已修项、旧行号和建议，实施前需复查当前源码。最新系统审计见[L1 接口审计](L1基础接口契约与现状审计.md)与[DSH 接入审计](DSH测试接入审计.md)。

一局真人对局的实测记录，用来驱动技法层修复。主持侧为读局势所核的代码位置一并给出。

## 局况

- 名册两方各一个实例：Alpha（Alliance/韩国，探针 14521）、Beta（Americans，探针 14522）；`UnitCount=0`、`Credits=10000`、`FogOfWar=No`、`spawnmap.ini`（144×144，MaxPlayer=2）。
- 起局：`python3 tools/start_match.py up --rule unit_count=0`，两侧都到 `STAGE_INGAME` 后派玩家 agent。
- 结果：Beta 经济与军力占优（11 台灰熊、7 栋建筑完好），Alpha 被断矿（4 台矿车被打掉、重工被拆），但 **Beta 始终未能定位并拆掉 Alpha 的建造厂**——直接原因是下面第 8、9、12 条。
- 全部证据来自 `status` 实读与两位玩家的 `call` 参数，未改任何技法代码。

## 缺陷

### 1. 远距离移动静默卡死：在管状态与实际位移脱钩

- 现象：`advance_to_cell` / `advance_covering` 受理成功、`status` 恒报「在管｜moving N」，但单位格坐标几百帧不动，最后才报 `failed`，**全程无告警**；模型无法从在管段判断任务是否已废。
- 样本：警犬 220、灰熊 233、灰熊 244、矿车 229（200 帧挪 4 格）、矿车 252（帧 17047~17758 卡在 (39,80)，约 700 帧后 `failed｜到位 0 失败 1`）、矿车 227/231（Beta 侧，最终 `failed 失败 2`）。
- 代码：`runtime/micro.py:26`（`arrive_radius=1`）、`:277`（90 帧不动才计 `retries`）、`:454`（重新下令即重置计时）、`:469`（`STUCK` 才再下令）、`:415`（`retries > max_retries` 才 `FAILED`）。
- 影响：模型把「在管」当作「在路上」，白等数百帧（Alpha 因此误判金线在走）。
- 修法建议：在管段带上目标格与「已 N 帧未位移」；超过 `stuck_frames` 发一条限频告警；重新下令不要无条件重置静止计时。

### 2. `scout_area` 对脚下/紧邻的未探索格立即 satisfied

- 现象：单位已出门、可正常移动，`call scout_area` 仍当拍 `satisfied｜到位 1`，格坐标不动、无失败无告警。
- 代码：`tactics/builtin/scouting.py:100` 取「最近」的未探索格（可能就是本单位所在格的邻格），而 `runtime/micro.py:275` 把「距目标 ≤ `arrive_radius`(1) 格」判为到位 → MoveTo 成为空操作。
- 影响：地面与空中侦察同时失效；配合第 8 条，本局两方都无法主动开图。
- 修法建议：候选格排除切比雪夫距离 ≤ `arrive_radius` 的格，取前沿里更远的一格。

### 3. `harvest` 同一根因，且对正在采矿的车有害

- 现象 a：`harvest` 对距矿点 ≤1 格的车报 `satisfied` 而车不动（Alpha #229/#237、Beta 227/231 复现）。
- 现象 b：对已在采矿的车再 `call harvest`，它从「采矿中」掉回「警戒」（Alpha 帧 ~10400 实测）。
- 代码：`tactics/builtin/economy.py:135`（`nearest_ore` 同样取最近格）、`:156`（停工判据只用 `mission`，不看实际是否在采）。
- 对照：Alpha 把 #237 放生 400+ 帧后它自行恢复采矿（帧 10060 起稳定「采矿中」）——**引擎会自己接管，是技法把它钉住**。
- 修法建议：目标格距单位 > `arrive_radius`；`mission == HARVEST` 一律不碰；停工判据加入实际开采状态。

### 4. 矿车不会被派往远处矿田，收入锯齿在 `status` 上不可见

- 现象：`nearest_ore` 只在 `ORE_SEARCH_RADIUS=40` 内找已探索矿格，找不到就不下令；自动层因此从不把矿车派到远矿田，工人手动 `advance_to_cell` 过去后采矿完全正常。
- 另一实测：单次往返 800~1000 帧、一次卸货 +400~800，收入天然是锯齿；矿车满载/卸货受阻在 `status` 里没有任何字段，只能靠盯金数反推。
- 代码：`tactics/builtin/economy.py:29`（`ORE_SEARCH_RADIUS`）、`:158`。
- 修法建议：无近矿时扩大搜索半径或报「附近无矿」；`status` 暴露矿车状态（满载/往返/卸货受阻）与附近矿田余量。

### 5. `has_pending_building` 用 `in_limbo` 判「完工待放置」

- 现象：建筑一开工就进 limbo，于是 2/54 时 `status` 与唤醒都报「完工待放置」；此时 `call place_ready_building` 会被受理并占住建造厂直到真完工（Beta 放重工实测 1290 帧，期间所有 `build_structure` 被拒「这个厂正忙」）。
- 代码：`tactics/conditions.py:111`（只看 `obj.in_limbo`）、`tactics/builtin/construction.py:27`；事件侧同一语义见 `engine/events.py:231`。
- 修法建议：判据加上 `progress_timer >= PRODUCTION_STEPS`；`status` 的「生产」行与「待放置」段不要同时声称同一栋。

### 6. `train_unit` 与 `build_structure` 共用 `_produce`，不校验类别

- 现象：`call train_unit`（`units=[213]` 建造厂、`type=GAPOWR`）受理后报 `satisfied`，但生产线上没有电厂、钱也没扣——错用被引擎静默吞掉。
- 代码：`tactics/builtin/production.py:30`（`_produce` 只解析类型、查重、发 `Produce`，没有单位/建筑类别校验）。
- 修法建议：按卡片名分流校验 `type_pointer` 的类别，不匹配抛 `TacticError`。

### 7. 自动层 `keep_harvesters` 与模型 `train_unit` 抢同一条载具单线

- 现象 a：模型 `train_unit(MTNK)` 受理 `satisfied` 后产出的却是 Chrono Miner；`keep_harvesters` 会自动把矿车补到 `target=4`，而载具生产是全局单线。
- 现象 b（本局终局直接成因）：Beta 金 24、全部可造项「钱不够」时，自动层仍排上一张 CMIN 1400 的单（`Chrono Miner 26/54 已暂停`），占住唯一产线并继续抽资金；同一局内它还在建筑队列中途把一栋 GAREFN 换成矿车单（帧 27339 前后）。即自动层的「补矿车」会在模型最没钱的时候锁死经济。
- 代码：`tactics/builtin/economy.py:238`（`keep_harvesters`，`trigger=Trigger.every(POWER_EVERY_FRAMES)`）、`:175`（`_line_busy` 只看 `queued_objects`，是观测态、非原子）。
- 修法建议：明确「模型订单优先」，自动层只在工厂真空闲时补；或给自动补车一个可被模型关闭的开关。

### 8. 空中单位仍走地面 `cell_passable`

- 现象：火箭飞行兵 253 对 (20,20)/(125,30)/(130,75)/(120,90) 等目标格全部被拒 `invalid cell`；黑鹰同理，空中侦察不可用。
- 代码：`tactics/builtin/micro.py:163,202`（`advance_to_cell` / `advance_covering` 的 `requires` 都含 `cell_passable`）、`tactics/conditions.py:245`（只看地面 `land_type`）。
- 修法建议：按单位类型分流，`SpeedType=Fly` / `AircraftTypes` 跳过 `cell_passable`（只判 `in_bounds`）。

### 9. `cell_passable` 拒绝不回传原因

- 现象：`(18,59)`、`(23,55)`、`(26,51)`、`(29,49)`、`(40,38)`、`(70,45)` 等被拒时只得到「目标格不可通行或在地图外（水、岩石、墙）」，模型只能逐格试错；探测不到 `map_data` 的那一拍也用同一句话。
- 代码：`tactics/conditions.py:64`（`HINTS` 单一话术）、`:257`（只判 `land_type`）。
- 修法建议：回传具体 `land_type`（水/岩石/墙）与「这一拍没读到地图」的区分；或提供一张粗略可通行带。

### 10. 己方但在 limbo 的单位报「不是你方可用单位」

- 现象：`focus_fire` 对刚进厂（进 limbo）的黑鹰返回「这些 id 不是你方可用单位」，而同一拍的 `status` 仍把它列在己方单位表。
- 代码：`command.py:906-919`（`_unknown_units` 只区分「敌方」与「其他」）、`engine/observation.py:46`（`units` 属性过滤 `in_limbo`）。
- 修法建议：单列「己方但在 limbo（进厂/装载/建造中）」，回一句「它当前不可指挥，等它出来」。

### 11. 唤醒流投递陈旧/开工事件（本局 7+2 次空唤醒）

- 现象 A（陈旧重放，Alpha）：帧 23008/23433/24136/24861/25592/26086/… 连收 7 条「建筑完工待放置」，内容为 **Alpha 自己**开局到中期的建筑完工**严格前缀**（GAPOWR#214 → GAPILE#217 → GAREFN#219 → GAWEAP#226 → GAPOWR#230 → GAAIRC#234 → NASAM#238），送达时那栋楼早已落地；每拍 `status` 与 `place_ready_building` 都确认「没有待放置」。玩家给出的前瞻预测后续依次命中，跨实例串扰可排除。
- 现象 B（开工即报，Beta）：帧 ~26483 收到「完工待放置：Allied Ore Refinery」，同拍 `status` 显示该矿厂 `进度 9/54`、无「待放置」段——与第 5 条同一根因，只是走事件流。
- 代码：`engine/events.py:231`（`_detect_placement`）、`wake.py:126`（注释里已记有同一现象的先例：「帧 29750 的『建筑完工待放置』投到 55660 才到」）、`wake.py:190`（`_prune` 只在 `_payload` 里被调用）。
- 现象 C（损失类同样重放，同一玩家）：帧 ~27000 收到「损失 1 个：Allied Attack Dog」，而那只警犬帧 ~7452 就已阵亡、此后该方再无任何单位；滞后量级与建筑事件一致（约 19500 帧）。**损失类是设计上要打断决策的高优先级事件，重放代价更大。**
- 玩家能看到的唯一字段：`唤醒未送达 N 条：- 距上次不足 180 帧，已并入待发队列｜- <事件> ×N`（帧 ~501、~21347、~22628 各出现一次）。即派发走的是**限流攒队**那一支；`sent`/`error` 之类字段只在未送达时渲染（`command.py:411-417` 只渲染 `self.wakes`，成功投递的记录不出现），故「唤醒已送达但 status 不提」不是第二个 bug。
- 量化（Alpha 自算，真实完工帧 vs 唤醒到达帧）：滞后从 ≈22000 帧单调收敛到 ≈14100 帧（GAPOWR#214 1002→23008、GAPILE#217 1486→23433、GAREFN#219 2918→24136、GAWEAP#226 4371→24861、GAPOWR#230 5472→25592、GAAIRC#234 6400→26086、NASAM#238 7778→26488、GATECH#247 13580→27702），即 12578 帧的历史被压缩进 4694 帧播完（压缩比约 2.7×），唤醒间隔实测 400~770 帧。**这不是固定延迟重放，而是积压队列以快于实时、受节流的速率在排空，且没有过期淘汰。**
- 推断（未定论）：待发项的时间戳疑似在每次重试时被**重盖成当下帧**，于是 `_prune` 的「发生到现在隔了多少帧」（`wake.py:190`）永远算出 0，陈旧项永不失效，直到限流放行时被 `_payload` 合并投出（`wake.py:203`）。若成立，这也解释了为什么代码注释里早有同类先例却没被 `_prune` 拦住。
- 修法建议（按代价排序）：① 队列加 TTL——入队记事件时间戳，出队时 `now - stamp > TTL`（几百帧量级）直接丢，无论排空速率如何都不再把几万帧前的完工/损失当成当前事件；② 待发项时间戳固定为**事件发生帧**，`_prune` 在每次 `request` 都跑并加 `0 <=` 保护；③ 同一事件按 id/游标去重，不因限流反复入队；④ 派发前用**当前观测**复核该对象是否仍待放置（统一走第 5 条的新判据）；⑤ 至少把事件原始帧号带进文本，让模型一眼看出是旧事。
- 影响：该类唤醒会打断决策且额度有限（`config/wake.json`：一局 30 次、两次间隔 ≥180 帧），空唤醒会挤掉「掉单位/掉建筑/被渗透/出局」。
- 修法建议：事件按时间戳出队并丢过期（迟到超过 N 帧直接丢）；派发前用**当前观测**复核该对象是否仍待放置；判定「完工待放置」统一走第 5 条的新判据。

### 12. 间谍卫星不生效

- 现象：Alpha 造出 GASPYSAT（1500，帧 14952 落成），此后 2600+ 帧全图始终不显示任何敌方建筑，只有零散敌方单位；1500 金白花，且直接导致全场盲打。
- 代码：`data/rules.py:36`（`SpySat` → `spy_satellite` 只是目录旗标），全仓没有第二处引用；观测可见性只看 `Cell.shrouded`（`engine/observation.py:126`）。
- 推断：引擎把「全图揭示」实现为 House 级状态，逐格 `AltFlags` 不变，探针没读这个通道。
- 修法建议：先测绘引擎如何表达 reveal（House 级标志位），再决定是接进观测还是判为不支持。

### 13. 能力缺口：无超武/伞兵卡片

- 现象：AMRADR（美国空军指挥部）建成后，`rulesmd.ini` 的 `AmericanParaDropSpecial`（8×E1）无法触发；`tactics` 里按「伞兵」筛为空。
- 现状卡片共 20 张：`advance_covering`、`advance_to_cell`、`auto_harvest`、`auto_opening`、`build_structure`、`deploy_mcv`、`engage_nearest`、`focus_fire`、`guard_area`、`halt`、`harvest`、`hold_and_fire`、`hold_position`、`keep_harvesters`、`keep_power`、`place_ready_building`、`report_trouble`、`retreat`、`scout_area`、`train_unit`。占领/工程师、修理、变卖同样没有卡片。

### 14. `status` 缺战略信息源

- 现象：没有已探索比例、没有「见过的敌方建筑与矿区方位」汇总、没有矿田余量；两方都只能靠单位视野逐格硬趟，本局因此都找不到对手基地。
- 修法建议：`status` 补一段「已知敌情摘要（已探索比例、见过的敌方建筑与最近矿区方位）」；这属于信息可见性，不改玩法判定。

## 非缺陷但易误读

- `satisfied` 早于单位真正进场：`train_unit` 报 `satisfied` 时单位还在队列里，要等它出门才出现在「己方单位」。
- 放置类意图的进度显示为 `moving`：`place_ready_building` 等楼完工期间，在管段看不出「在等建造完成」。
- 自动层默认把矿车补到 4 台、建筑按电厂→兵营→矿厂→重工地梯补齐：模型不介入时它照跑，钱不够时会把资金吸干（Alpha 本局「金 18」即暂停产线即时吃钱，而非零收入）。
- 收入模型：单矿厂单卸货口下收入是「长时间 0 → 一次性 +400~1500」的锯齿，`status` 上无从预判。
