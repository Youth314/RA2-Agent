## 阻断级

没有这两条，「建造」这条链写不出来——不是缺技法，是能力上做不到。

### R1 让 limbo 中的己方对象可寻址

**现状**：`Observer.observe` 丢掉所有 `in_limbo` 的己方对象（[observation.py:116](../../../src/ra2agent/engine/observation.py#L116)），`UnitPool` 的「指针 → agent id」索引又从 `observation.own` 建（[command.py:117](../../../src/ra2agent/command.py#L117)）。而完工待放置的建筑正在 limbo——`executor._placed` 的判据是 `found.on_map and not found.in_limbo`（[executor.py:123](../../../src/ra2agent/runtime/executor.py#L123)），即放置前在 limbo、放置后才进地图。

**后果**：技法看不见它，`ctx.subject.agent_id(pointer)` 也拿不到它的 id，而 `Place` 的载荷 `building: int` 只收 agent id。故**没有任何技法能产出一条 `Place`**。`Deploy` 能用，只因基地车在地图上、不在 limbo。建造厂一次只做一单，第一栋放不下去就永远卡在第一栋，整局没有经济。

**需要的接口**，二选一：

- 最小：`UnitPool._pointers` 额外收进「己方且 `in_limbo`」的对象，`agents()` 不变（limbo 对象不是可用单位）。
- 更干净：`Observation` 增一列 `own_pending: tuple[GameObject, ...]`（己方在 limbo 中的对象），`UnitPool` 按它建指针索引。

推荐前者：两行改动，语义已够。后者要动观测层的公开字段，等有第二个用例再动。

**用途**：`place_ready_building` 把 `factory.object`（引擎指针）换成 agent id，发出 `Place`。

**验收**：单测里 `state` 含一栋 `in_limbo=True` 的己方建筑与一条 `completed=True` 的 factory，`UnitPool(observation, identity).agent_id(factory.object)` 返回非 `None`，且该 id 不出现在 `agents()` 里。

### R2 放置合法性：合法格必须由观测层带进来

**现状**：放置格合法性只有引擎说了算，实测是用 `PlaceQuery` 问出来的（[tools/survey.py](../../../tools/survey.py) 的 `test_build`）。但 client 与 executor 都没有这条路——`Executor._ROUTES` 里 `place` 直接走 `PlaceBuilding`（[executor.py:226](../../../src/ra2agent/runtime/executor.py#L226)）。故技法只能猜一个坐标，不合法就吃 `placement_blocked`。

**约束**：不能让 L0 去挑格——「L0 从不选择」是设计支柱（[executor.py:4](../../../src/ra2agent/runtime/executor.py#L4)）。也不能让技法自己发查询——技法不做 I/O。故合法格只能**经观测层流到技法层**。

**需要的接口**：`Observation` 增 `placement_sites: tuple[tuple[int, int], ...]`，内容是「当前待放置建筑的一部分合法格」，由观测层在发现 `completed` factory 时查询并缓存若干帧。

备选（不改观测层）：`Client` 暴露只读的 `place_query(pointer, cells) -> tuple[cell, ...]`，由指挥层在 `status` 里附上，模型再把它当参数传回 `call place_ready_building(cell=...)`。缺点是多一次模型往返。

推荐前者，理由：放置是自动层该自己做完的事，不该占模型一轮。

**验收**：技法能在不发命令的前提下，从观测里读到至少一个合法格。

## 高价值

不影响能不能写，影响写得好不好。

### R3 脉冲的跨帧记忆

**现状**：`Autopilot._pulse` 调 `registry.run(...)` 时不传 `memo`（[autopilot.py:83](../../../src/ra2agent/runtime/autopilot.py#L83)），`TacticRegistry.run` 于是每次新建 `{}`（[core.py:463](../../../src/ra2agent/tactics/core.py#L463)）。故 `ctx.remember/recall` 对脉冲等于没有，`ctx.attempt` 对脉冲恒为 0。

**后果**：脉冲写不出重试、退避、去重与差分。我被迫用 `frame // 间隔` 轮换候选格来假装重试。

**需要的接口**：`Autopilot` 为每条技法名保留一份 memo、跨帧复用，传给 `registry.run(memo=...)`；生命周期为一局（一局结束或技法库重载即清）。

同时希望把上次结果喂进来：`ctx.last_outcome: dict | None`，形如 `{"frame": int, "error": str | None, "intents": int}`。

**验收**：一条脉冲技法能在第二次运行时读到第一次写下的 memo，并据此换一个落点。

### R4 技法体能读到事件

**现状**：`Trigger` 只能声明「哪类事件来了跑一次」，命中判定只看事件**种类名**的集合（[autopilot.py:48](../../../src/ra2agent/runtime/autopilot.py#L48)），而 `TacticContext` 的构造参数里没有事件（[core.py:215](../../../src/ra2agent/tactics/core.py#L215)）。

**后果**：`Trigger.on("low_power")` 触发后，技法读不到电力数值，只能从观测反推，等于事件白给。

**需要的接口**：`TacticContext` 增 `events: tuple`，内容为本拍事件（或本次触发命中的那些）。

**验收**：一条 `Trigger.on("low_power")` 的技法能读到导致它运行的那条事件及其主语。

### R5 损失与被攻击的事件

**现状**：`EventKind` 只有四个：`LOW_POWER`、`INSUFFICIENT_FUNDS`、`INFILTRATED`、`PLAYER_DEFEATED`（[events.py:37](../../../src/ra2agent/engine/events.py#L37)）。

**后果**：「基地在挨打」与「我掉了一个单位」没有任何通道。自动层只能退回几何接近（`wake_on_base_attack` 只能这么做），模型只能自己比对名单——上一局 4 辆 Grizzly 与 3 个 GI 的死，是靠 `status` 里「己方 N」的变化发现的。

**需要的接口**：新增 `UNIT_LOST` 与 `BUILDING_ATTACKED`（或 `STRUCTURE_DAMAGED`）两种 `EventKind`，带 `Subject` 与对象的 agent id；`status` 报出来。

**验收**：一局里掉单位后，下一次 `status` 出现「损失 214 Grizzly Battle Tank」。

### R6 `status` 报电力与生产

**现状**：`House.power_output/power_drain/is_low_power` 都解析了，但 [command.py](../../../src/ra2agent/command.py) 里搜不到一处 `power`；生产侧只有 `layer.progress()`（在管任务），没有建造进度。

**后果**：模型看不到电力水位，也看不到「手上有没有待放的建筑、在造什么」。上一局 10 分钟里，我对自己基地的产能状况一无所知。

**需要的接口**：`StatusReport` 增 `power` 与 `production` 两段；`production` 每行给进度 `progress_timer/PRODUCTION_STEPS`、是否 `completed` 待放置、是否 `on_hold`、在造的类型名（若 R7 成立）。

**验收**：`status` 文本里出现电力与建造进度各一行。

### R7 生产队列里是哪个类型

**现状**：`Factory.queued_objects` 是对象指针，引擎不回报类型（[executor.py:131](../../../src/ra2agent/runtime/executor.py#L131)）。

**后果**：`Produce` 的生效判据只能是「队列快照变了」（`_factory_snapshot`），技法答不出「电厂在造了吗」，只能保守成「手上还有活就不下新单」——这是写 `build_base_order` 时被迫接受的语义损失。

**需要的接口**：`Factory` 增 `producing: ObjectType | None`（在造类型的条目）。若引擎确实不给，退路是 R3：技法用自己的 memo 记「我发过什么单」，够用但会与手动操作脱节。

**验收**：技法能判断「某类型是否正在生产」，而不是「有没有活在手上」。

## 一致性与安全

### R8 门顺序把有用的错误挡住了

**现状**：`Commander._accept` 先按**全池**评适用条件（[command.py:422](../../../src/ra2agent/command.py#L422)），再校验模型点名的具体单位（[command.py:431](../../../src/ra2agent/command.py#L431)）。单位全死光时全池为空，返回的是条件名；真正有用的「这些 id 不是你方可用单位」在后面，永远轮不到。

上一局收到的就是「未受理 engage_nearest：此刻用不上：has_units」——我读成「技法条件不对」，实际是「你点名的单位刚刚全死了」。

**需要的接口**：把单位校验挪到条件闸之前；并让 `CallResult` 带一个稳定的 `reason` 码（`no_units`、`unknown_units`、`condition_missing` 一类），`error` 保留人话。

**验收**：指名已阵亡的单位时，返回「这些 id 不是你方可用单位」，而不是条件名。

### R9 `timeout_ms` 要么强制，要么删掉

**现状**：`TacticPolicy.timeout_ms` 声明了（[core.py:294](../../../src/ra2agent/tactics/core.py#L294)），`to_dict/from_dict` 也带它，但 `src/` 里没有任何地方用它。

**后果**：配置声称「技法 50ms 超时」，实际上一条扫全图的技法会卡住 tick 线程。

**需要的接口**：真按它中断技法调用（不能强杀线程的话，至少在超时后记一条 `tactic_slow` 并停用该技法），或者把字段删掉，别给人虚假的保护感。

**验收**：一条故意睡满的技法被测出超时。

### R10 模型指挥建造的通道（要一次产品决策）

**现状**：脉冲与被调用是两个不相交的世界。脉冲的 subject 是全池、参数只能取默认值（必填参数在登记期就报错）；被调用的 subject 是模型点名的编队。而建筑既不在任何编队里，也不在 `status` 的单位清单里（R1 的后果之一）。

**后果**：**模型无法指挥建造**。想让模型说「造个矿厂」，只能把顺序硬编码进技法，或靠 `Wake` 一问一答。

**需要的接口**，三选一，我倾向前者：

- 允许 `call` 的 `units` 为空，使无单位的动作也能由模型带参发起；
- 或加一个「阵营级参数」通道，使脉冲也能读到模型最近一次下达的参数；
- 或接受现状：建造顺序全由技法常量决定，模型只通过 `Wake` 干预。

**验收**：模型一条 `call` 就能做到「造 GAREFN」，不用改代码。

## 上线前需要的一次测绘

以下均为推断，未在真机确认；确认前相关技法只留在 `tactics/local/`。

1. 一栋 `completed` factory 的 `object`，在 `state.objects` 里是否 `in_limbo=True`。决定 R1 的最小方案够不够用。
2. `PlaceQuery` 的合法格集合是否稳定：同一栋建筑连查两帧，集合是否一致。决定 `Observation.placement_sites` 能缓存多久。
3. 放置完成后 `Factory.progress_timer` 是否归零。决定「忙」的判据能否从「有进度」收紧到「有进度或待放置」。
4. `PlaceBuilding` 曾在真机上成功返回后崩溃，之后三种对照未复现（见[交接](../交接.md)）。建造类技法上线要有单独开关，首次真机跑要留证。
