# L1 基础接口契约与现状审计

日期：2026-10-02。对应[演进计划](../../notes/设计/L1基础能力与技法演进计划.md) S1。已完成源码静态审计和最小契约草案；现有 Move / Stop 链路已落实首轮执行安全与离线回归，具体实现、证据与未完成范围以[接口离线验证](../../notes/验证/MoveStop接口离线验证.md)为准；完整候选契约与新原版操作尚未实现；S3 只读原版事件输入已接入，范围见[事件接口验证](../../notes/验证/原版事件接口验证.md)；现有链路真机验证范围以验证记录为准。玩家操作的原版依据与待测项见[能力表](../../notes/引擎/玩家操作能力表.md)，DSH 接入见[测试接入审计](../../notes/验证/DSH测试接入审计.md)。

## 1. 审计结论

现有意图、序列化、执行器、校验器、技法注册与运行时可作为扩展基础。首批能力不能只靠新增几个 Mission 编号落地：目前缺少原生 Guard/Escort/Harvest 路由与动态观测，且命令验证、任务结算、重试、租约与身份变化已有语义差距。

保留 L2 只调用技法、L1 构造类型化意图、L0 校验并执行的边界。基础能力首先服务 L1，不要求全部注册成公开技法；未知的引擎路径明确标 unsupported，不能用普通 Move/Stop 的替代实现冒充原版行为。

### S2 对候选契约的初步约束

S2 已取得首轮人工玩家事件与效果对照，事实和适用范围在[能力表现场记录](../../notes/引擎/玩家操作能力表.md#s2-现场记录)维护；尚未验证 DLL 新下令路径，不据此把候选能力标为已实现。

- 区分玩家操作、引擎输入事件与对象后续 Mission。原生逻辑可以转入另一任务；固定 Mission 等值不能作为所有类型的统一生效或完成条件。
- 目标类别和上下文先于字段名。地点、单位和建筑需类型化处理；不能仅因协议存在 follow 字段就选定护送实现，也不能用 destination 单独确认持续对象目标。
- 显式单次维修与长期维修护送的生命周期。一次上下文追随维修结束后，长期技法是否重新建立操作、保持租约、筛选新伤车及恢复经济，仍由任务政策定义；不能默认原版事件永续。
- 乘员、当前模式与目标健康可能影响上下文动作。能力未知时不能根据静态武器断言可维修；装卸对象的 limbo 变化不能统一解释为死亡。
- 正式解析事件必须按 event_type 分派并隔离残留 oneof；未解析的 Idle 对象载荷、对象 Target 与模式回读是后续证据缺口。事件记录证明输入线索，实际效果仍需对象和结果观察。

这些约束收敛 S3 的调查与接口设计，不授权把任意 Mission 或事件直接公开给模型。优先验证受控原版翻译及最少动态回读，保留无法确认与部分拒绝的表达。

### S3 首批实现顺序

第一部分已完成只读原版事件输入，接口、回归、对象编码限制与构建现状在[事件接口验证](../../notes/验证/原版事件接口验证.md)维护。后续优先 GuardCurrent / GuardPosition，调用者仍使用 Agent 稳定 ID 与类型化地点；当前锚点在发送前按新鲜单位状态确定，不由模型传原版地址、TargetClass 编码或任意 Mission。

下令只通过经过能力检查的受控 DLL 路径。旧 DLL 缺少新操作时明确 unsupported，不尝试危险通道再将服务端错误当成支持检测。输入事件可以补充观测证据，但对象 ID 映射与持续状态缺失时不将其提升为 applied。原生经济与维修后续 Mission 可变化，验证条件逐类定义；一次性操作建立后是否释放租约由技法生命周期声明。

对象护送、维修目标与长期组合的适用性分开收敛，不能仅因为候选底层任务相似而抹去原版上下文与完成条件差异。新请求字段、能力声明与 DLL 新增编号在建立可复现构建与补丁后确定；现有 Move / Stop 保持兼容，采矿 / guard_area 迁移属于后续阶段。

## 4. 最小契约草案

以下为语义契约，标识符为候选。实现时尽量复用现有 Intent 信封与注册表，不要求同时引入全部新类。

### 4.1 操作请求与任务分离

TacticCall 保持任务目标与 TTL。L1 向 L0 发出可序列化的操作意图，操作有独立 request_id 和回执；同一任务可以先后发多个操作。命令生效后，薄技法可结束；长期组合技法继续监测任务目标并持有租约。两者都不能把“原版行为继续运行”解释为需要每拍重发。

| 字段/概念 | 最小语义 |
|---|---|
| match_id / player_id | 局次与席位；重连/重开后旧 ID 和请求不可复用 |
| request_id / attempt_id / parent | 同一逻辑操作、每次发送尝试及父任务；日志可以关联，不能假定引擎支持去重 |
| operation | 玩家语义的受控操作集合；不开放任意 Mission/地址 |
| actors | 稳定 ID 集合，逐单位校验；控制对象与目标对象分开 |
| target | 类型化 None / Cell / Unit / Structure；HarvestAt 用明确矿格，不隐式寻找任意目标 |
| basis_frame / valid_until | 决策依据与有效期；发送前复查，可因状态变化拒绝；wall timeout 仅控制等待 |
| issuer / scope / authority | 来源与授权作用域；必须证明 actors 属于该任务/脉冲可控制集合，不能只相信技法自己填的 scope |
| execution policy | 单次下令或建立原生持续行为；重试类别与命令替换语义由操作定义，不由任意参数绕过 |

最小新增类型可为 Stop、Guard、GuardPosition、EscortUnit、GuardStructure、HarvestAt；MoveTo 先保留 passive/aggressive 并明确说明，逐步迁移 hold。是否将 Move/AttackMove 拆成独立类在实施时定稿。未知原版 Guard 路径保持 unsupported，不注册成可执行 Mission 包装。

### 4.2 回执与任务结果

回执建议逐单位记录 local_rejected、submitted、engine_rejected、observed_match、unverified。状态包含发送/观察帧、依据、拒绝原因与错误原文。submitted 只表示请求提交，不证明游戏接受；传输中断时是否已提交可未知。observed_match 只表示观察匹配，若状态下令前已成立，应注明 preexisting_match，不能宣称本次请求导致变化。

建立原版事件确认能力后才可增加更强的 applied/ack 证据等级。STOP 已经处于停止状态时，目标可满足，但不能伪造本次指令执行确认。新 AttackMove 至少需要能区分移动模式的证据；只看 destination 不足。

任务结果另记录 completion_basis、逐单位 completed/failed/unverified、目标是否满足以及部分完成。薄技法可声明 completion_basis=operation_observed；移动到位等组合任务声明 goal_satisfied。不再让 ARRIVED 泛指生产、警戒、装载和所有新操作。all/any 等聚合条件由任务声明，默认全体完成；当前默认已改为全体完成才 SATISFIED；其他聚合条件尚未提供任务级声明。

### 4.3 能力与合法性

能力查询同时表达“接口支持状态”和“此对象当前适用性”。前者区分已测、源码候选、未接入；后者用 yes/no/unknown 并给原因和所需状态。不能把缺少 IFV 模式或乘员信息的 unknown 当作已支持或明确不支持。

最小观测优先补己方实际 Target、Follow、可执行状态/运动域、乘员或 IFV 当前模式、矿车货量与采矿阶段。能否读取及何种字段可靠仍需 DLL 源码和真机核验。敌方字段仅在合法可见时提供；当前灰雾、隐形等可见性不足不能用全量 state 补齐。

对象点名须尊重合法观测；地点允许前往未探索格，不授予获取隐藏资源/对象信息的能力。原生 Guard/Harvest 自主选目标属于原版行为；L1 主动选对象目标不得借全量 state 找隐藏对象。

### 4.4 取消、重试与租约

cancel 默认结束 Agent 任务并交还管理权；停止单位必须显式 Stop。联动取消并停止时逐单位报告结果，不能保证原版队列被全部清空。原生行为持续期间的任务是否持有租约、何时允许自动层重新接管，应在技法元数据中声明。

Timeout/GameNotResponding 后先回读、等待游戏恢复，再按操作类别决定是否重试。移动也可能重置寻路，不能无条件当绝对幂等；部署切换、装卸、生产、追加路点等未知结果禁止盲重发。Agent request_id 可以防本地重复处理，但不能提供游戏端 exactly-once。

统一仲裁覆盖模型任务、Micro 内部调用和 Auto 脉冲：actors 必须在授权作用域内，自动层默认避让在管单位，授权替换要留痕。归属变化、租约取消和 TTL 到期均在实际下令前重查。

## 6. 旁支问题与范围控制

Executor.plan 宣称纯规划，但 Place(cell=None) 会经 _nearest_place_cell 调 client.place_query（executor.py:436）；新接口应将需要 I/O 的准备与纯规划分开。此次首批单位操作不必先改完建筑流程，但离线回放不能声称任意 plan 都没有 I/O。

command_sent 已移到 _deliver 返回后；发送层 Timeout 与等待超时保留 plan、intent、提交依据和未知记录。该日志仍不是引擎执行确认。

identity._refresh 不更新 house（identity.py:142）；当前 ownership 仍以 GameState 校验，但跟踪记录不能作为权威归属。guard_area 的 max_frames 在技法被再次调用时检查，ENGAGING 状态可能不再调用技法（micro.py:268、466）；应由任务生命周期处理期限，不能把旧组合行为当原版 Guard 验证。

## 8. 建议实施顺序

1. 先落实回执、部分结果、请求关联、发送前状态复查、租约/作用域与帧推进门控；规范现有 Move/Stop，按 C01–C09 验证。
2. 按 T01–T04 测绘原版行为和所需观测，选经过核验的事件/调用路径；未知能力继续 unsupported。
3. 逐项接入 Guard/GuardPosition/EscortUnit/GuardStructure/HarvestAt；保留受控类型与操作特定生效判据。
4. 薄技法和组合技法使用同一基础接口，再迁移旧卡片和自动经济；DSH 只在集成阶段验证实际玩家会话。
