# 命令接口源码结论

从 ra2yrcpp 源码读出的命令接口语义，作为适配层 API 的依据。线上实测的结论见[探针实验结论](探针实验结论.md)，两者冲突以实测为准。

依据文件：`src/commands_game.cpp`、`src/commands_yr.cpp`、`src/commands_builtin.cpp`、`src/command/command_manager.hpp`、`src/instrumentation_service.cpp`、`src/constants.hpp`、`src/hooks_yr.cpp`、`src/ra2/common.cpp`。
proto 定义见 [`proto/ra2yrproto/`](../../proto/ra2yrproto/)，取自 [shmocz/ra2yrproto](https://github.com/shmocz/ra2yrproto) 提交 `0ad72455`。

## 命令清单

命令按 protobuf 全限定类型名注册。服务端取 `Command.command` 的 `Any.type_url` 末段查表（`instrumentation_service.cpp::handle_cmd`），类型名不符时 `handlers_.at()` 抛 `out_of_range`。

「排队」指命令在游戏主循环线程执行，见下节。

| 命令 | 注册处 | 执行方式 | 参数 |
|---|---|---|---|
| `GetSystemState` | builtin | 同步 | 无，握手用 |
| `GetGameState` | yr | 同步 | 无，返回完整 `GameState` |
| `StoreValue` / `GetValue` | builtin | 同步 | `key`、`value`，服务端字节键值对 |
| `InspectConfiguration` | yr | 同步 | `config`、`update` |
| `ReadValue` | yr | 同步 | `data`，按设置的字段名取对应状态 |
| `UnitOrder` | game | 排队 | `object_addresses`、`action`、`target_object`、`coordinates` |
| `ProduceOrder` | game | 排队 | `object_type`、`action` |
| `PlaceBuilding` | game | 排队 | `building`、`coordinates` |
| `PlaceQuery` | yr | 排队 | `type_class`、`house_class`、`coordinates` |
| `MissionClicked` | yr | 排队 | `object_addresses`、`event`(Mission)、`target_object`、`coordinates` |
| `ClickEvent` | yr | 排队 | `object_addresses`、`event`(NetworkEvent) |
| `UnitCommand` | yr | 排队 | `object_addresses`、`action` |
| `AddEvent` | yr | 排队 | `event`、`frame_delay`、`spoof` |
| `AddMessage` | yr | 排队 | `message`、`duration_frames`、`color` |

## 执行模型

命令由 `CommandManager` 的单一工作线程执行（`command_manager.hpp::worker`）。

同步命令在工作线程内直接完成，`Command` 析构时把 `command_data_` 打包为结果。

排队命令经 `get_gameloop_command`（`hooks_yr.hpp:110`）把闭包投入 `GameCommandData` 的工作队列，并置 `pending=true`；工作线程随即返回，命令留在队列中。

`pending` 为真时 `flush_results` 不返回该结果（`command_manager.hpp:331`），因此排队命令的结果**在游戏主循环执行闭包之后**才可轮询到。主循环在 `GameLoopBegin`（`hooks_yr.cpp:379`）调用 `GameCommandData::consume_work()` 执行排队的闭包。

推论：`UnitOrder`、`ProduceOrder`、`PlaceBuilding`、`PlaceQuery`、`MissionClicked`、`ClickEvent`、`AddEvent`、`AddMessage` 一律要等主循环推进才生效；主循环不推进（失焦暂停）时其结果永不返回。

## 错误通道

排队命令的闭包抛 `std::exception` 时由 `Command::run_async_handler` 捕获，写入 `error_message` 并置 `ResultCode::ERROR`（`command_manager.hpp:112`）。

工作线程内抛出的异常由 `emplace_user_command` 捕获，同样写入 `error_message`（`command_manager.hpp:290`）。

两种情况都在 `flush_results` 中映射为 `CommandResult.result_code=RESPONSE_ERROR` 并回填 `error_message`（`instrumentation_service.cpp:51`）。

**因此命令失败经 `CommandResult.error_message` 返回，连接不中断。** 唯一绕过该通道的失败是游戏进程崩溃。

已知崩因：坐标越界时 `ra2::get_map_cell` 返回非空无效指针——`common.cpp:14` 直接调用 `TryGetCellAt`，无边界检查——`ClickMission` 随之跳转到地址 0。受影响的只有 `UnitOrder` 与 `MissionClicked` 的带坐标动作。

## 请求方式

`Command.blocking=true` 时，服务端把 `PollResults` 直接放进 `CLIENT_COMMAND` 的响应体（`instrumentation_service.cpp:102`），省去单独一轮轮询；为假时响应体是 `RunCommandAck`。

`queue_id` 即 WebSocket 连接的 `socket_id`（`instrumentation_service.cpp:103`），每连接一个结果队列。

基础收发流程见[探针实验结论](探针实验结论.md#命令通道)。

## 队列与限制

| 常量 | 值 | 含义 |
|---|---|---|
| `RESULT_QUEUE_SIZE` | 32 | 每连接结果队列容量；环形缓冲，溢出覆盖最旧结果 |
| `POLL_BLOCKING_TIMEOUT` | 2.5 s | `blocking=true` 时服务端等待结果的上限 |
| `PLACE_QUERY_MAX_LENGTH` | 1024 | `PlaceQuery` 输入候选坐标上限，超出静默截断 |
| `MAX_MESSAGE_LENGTH` | 1e7 | 单条 WebSocket 消息上限 |
| `EVENT_BUFFER_SIZE` | 600 | 事件缓冲容量 |
| `MAX_CLIENTS` | 16 | 并发连接上限 |
| `PRODUCTION_STEPS` | 54 | 生产动画步数 |

## 观测模型

每帧 `GetGameState` 返回的 `GameState` 由 `state_to_protobuf`（`hooks_yr.cpp:124`）就地更新 `StorageValue.game_state` 得到，含 `objects`、`houses`、`factories`、`cells_difference` 与事件列表。

**`GameState.map_data` 从不填充。** 地图只存在于 `StorageValue.map_data`（`hooks_yr.cpp:155`、`:172`），须经 `ReadValue{data{map_data}}` 或 `ReadValue{data{map_data_soa}}` 单独取一次；`map_data_soa` 是结构数组形式，repeated 字段按 packed 编码，体积远小于 `map_data`。

`object_types` 与 `prerequisite_groups` 每帧先清空，只在 `do_type_classes` 为真时重新填充（`hooks_yr.cpp:133`），因此只在首帧出现一次。

地图变化经 `cells_difference` 增量送达：`parse_map` 与上一帧逐格比较，只输出有变化的格子，`update_MapData` 再按 `Cell.index` 回填（`hooks_yr.cpp:165`）。

**观测模型因此是：开局取一次 `map_data_soa` 作底图，之后每帧 `GetGameState` 取对象与 `cells_difference` 增量。**

`parse_map_data_interval` 控制地图解析频率（`hooks_yr.cpp:166`）：仅当 `current_frame % interval == 0` 时才解析并产生增量。该值不得为 0，否则取模除零。

## 配置读写

`InspectConfiguration{update=false}` 返回完整配置；`update=true` 时经 `to_json` → `ConfigData::parse` → `MainData::update_config` 应用（`commands_yr.cpp:120`）。

`update_config` 只写入两个字段（`hooks_yr.cpp:75`）：`parse_map_data_interval`（仅当大于 0）与 `single_step`。其余字段即使发送也不生效。

`ConfigData::parse` 把 `parse_map_data_interval` 为 0 的情况强制改回默认值 1（`config.cpp:36`），与 proto 注释「Set 0 to disable」矛盾；关闭逐帧地图解析只能给一个很大的值。

## 单步模式

`Configuration.single_step` 为真时，主循环每帧在 `GameLoopBegin` 置 `game_paused=true` 并阻塞，直到该值被置假（`hooks_yr.cpp:391`）。

`GetGameState` 读到 `game_paused` 为真后把它置假（`commands_yr.cpp:104`），主循环随之放行一帧。

效果：每发一次 `GetGameState`，游戏恰好推进一帧。帧推进由 Agent 驱动，不受实时节奏约束。

该模式**不解除失焦暂停**：窗口失焦时主循环不进入 `GameLoopBegin`，阻塞点不会被到达，推理见[探针实验结论](探针实验结论.md#运行约束)。

## 实现缺陷

| 缺陷 | 位置 | 影响 |
|---|---|---|
| `UNIT_ACTION_NONE`(0)、`UNSELECT`(3)、`TRY_TO_DEPLOY`(4) 未列入 switch | `commands_game.cpp:110` | 落入 `default` 抛 `invalid unit action`；取消选中与尝试部署不可用 |
| `UNIT_ACTION_REPAIR`(9) 映射到 `Mission_Capture` | `commands_game.cpp:139` | 「维修」实为占领，与 `CAPTURE` 同义 |
| `ProduceOrder.action` 从不读取 | `commands_game.cpp:184` | `BEGIN`/`HOLD`/`CANCEL` 行为相同；暂停与取消须改用 `AddEvent` 的 `Suspend`/`Abandon`，见[测绘结果](命令能力测绘结果.md#生产队列的暂停与取消) |
| `ProduceOrder` 不设置 `is_naval` | `commands_game.cpp:202` | 海军生产可能失败 |
| `UnitOrder` 丢弃 `ClickMission` 的返回值 | `commands_game.cpp:97` | 引擎内部拒绝时不报错，只能靠状态复核 |
| `UnitCommand` 只实现 `DEPLOY`/`SELL`/`SELECT`，其余静默忽略 | `commands_yr.cpp:36` | 失败比 `UnitOrder` 更隐蔽 |
| `PlaceQuery.coordinates` 是输入候选而非输出 | `commands_yr.cpp:207` | 须自行生成候选坐标，不能一次查询全部合法位置 |
| `PlaceQuery.house_class` 传 0 不视为当前玩家 | `commands_yr.cpp:194` | proto 注释所称的留空兜底未实现，必须给真实 House 指针 |
| `House.build_state` 从不填充 | `state_parser.cpp` | 无逐项建造进度，只能看 `Factory.progress_timer` 是否到 54 |
| 命令失败时响应 payload 是请求的回声 | `command_manager.hpp:288` | 解析结果前必须先看 `result_code`，否则会把输入当成输出 |
| `add_event` 只处理五种载荷 | `state_context.cpp:68` | 仅 `production`、`place`、`sell_cell`、`sell`、`deploy` 会赋值 `EventClass.Data`，其余事件类型构造出的 `Data` 未初始化 |

## 前置校验清单

适配层发送前必须检查，不满足则在本地拒绝：

1. 坐标经 `Coord2Cell` 后落在地图范围内（`GameState.map_data` 的 `width`/`height`）。
2. `object_addresses` 中每个地址存在于当前 `GameState.objects` 且 `in_limbo=false`；否则 `get_object_entry` 抛 `object not found`。
3. 对象的 `current_mission` 不是 `Mission_None`(-1) 或 `Mission_Construction`(18)；否则抛 `illegal mission`（`commands_game.cpp:76`）。
4. `action` 属于已实现集合：`DEPLOY`、`SELECT`、`SELL`、`SELL_CELL`、`MOVE`、`CAPTURE`、`ATTACK`、`ATTACK_MOVE`、`STOP`。
5. `CAPTURE`、`REPAIR`、`ATTACK` 须给出 `target_object`；`MOVE`、`ATTACK_MOVE` 须给出 `coordinates`。
6. `ProduceOrder` 的目标类型须使 `HouseClass::CanBuild` 返回 `Buildable`，否则抛 `unbuildable`。
7. `PlaceBuilding` 的目标建筑须已完工，且属于当前玩家的某个工厂。
