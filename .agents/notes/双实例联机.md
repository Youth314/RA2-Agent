# 双实例联机

同一台机器上跑两个 `gamemd`，各由一个探针驱动，两边是真正的两人对局：帧同步锁步，双方的基地车会在图上会面。这是「Agent 对 Agent」与「人观战」的前提。

这条路要过**两道墙，而且解法不同**。只解一道都不够：补丁让两个进程能共存，但同会话里只有一个前台窗口，失焦的那个不推进，帧同步会把另一个也拖住。

## 一、墙一：单实例守卫（机器级）

`gamemd` 自己的 `Startup.CPP` 以固定名建互斥体，`GetLastError() == ERROR_ALREADY_EXISTS` 时把已有窗口置前、关句柄、从 `WinMain` 返回 0。

```text
006bbe56  push  0x840f14                 ; "29e3bb2a-2f36-11d3-a72c-0090272fa661"
006bbe5f  call  dword ptr [0x7e1248]     ; CreateMutexA
006bbe6a  call  dword ptr [0x7e1200]     ; GetLastError
006bbe70  cmp   eax, 0xb7                ; ERROR_ALREADY_EXISTS = 183
006bbe75  jne   0x6bbed6                 ; 不等 -> 正常启动
006bbe77  ...                            ; 已存在 -> 置前 + 退出
```

**第二个实例的表现是「干净退出」，不是崩溃**：退出码 0、无 WER、无转储、显示层日志约 130 ms 后 `detached successfully`（走的是 `ExitCode` 而非 `TerminateProcess`）。那句 "TibSun is already running...Bail!" 要经 `0x4068E0`，而它在发布版里已被 patch 成 `ret`，所以**永远静默**。

`tools/patch_single_instance.py` 把比较的立即数改成 `0xFFFFFFFF`（文件偏移 `0x2BBE71`），分支恒不成立，其余启动流程一字未动。`gamemd.exe` 与 spawn 版同址同字节，说明这是原版代码而不是 CnCNet 加的。

命令行参数与 INI 键都改不了这件事：GUID 是 `.data` 里的硬编码字面量，全 exe 只有 `0x6BBE57` 与 `0x6BBE7A` 两处引用。

同一函数里还有一个 AutoPlay 互斥体（`01AF9993-3492-11d3-8F6F-0060089C05B1`），它不拦人；该名字**没有 `Global\` 前缀**，所以是会话级的——这也是「两个终端会话不需要补丁」的依据。

## 二、墙二：失焦暂停（会话级）

主窗口过程在 `WM_ACTIVATE` 里写全局标志 `0xA8ED80`：

```text
007778ce  mov  ds:0xa8ed80, al          ; al = (wParam != 0)
```

主循环大量读它，活动性判定在 `0x77DE0C-0x77DE33`（`GetActiveWindow`/`GetForegroundWindow` 与主窗口句柄 `0xB73550` 比较）。**一个会话只有一个前台窗口**，所以同会话的两个实例里总有一个标志为 0；联机是帧同步的，退化的那个会把两边一起卡住。

解法是 **cnc-ddraw** 的 `windowed=true` 加 `noactivateapp=true`。它在窗口模式下吞掉 `WM_ACTIVATE`、`WM_ACTIVATEAPP`、`WM_NCACTIVATE`、`WM_KILLFOCUS` 四条消息，并且**不最小化**窗口。装法是把 `ddraw.dll` 换成 cnc-ddraw 并写一份 `ddraw.ini`；它的 `[game]` 段（`checkfile=.\blowfish.dll`，即 TS/RA2 预设）本来就有 `noactivateapp=true`，而该段不设 `windowed`，故继承 `[ddraw]` 段的值。

**DDrawCompat 的 `AltTabFix = noactivateapp(0)` 不管用，已实测。** 它只处理 `WM_ACTIVATEAPP`（`DDraw/DirectDraw.cpp` 的 `handleActivateApp`），而暂停由 `WM_ACTIVATE` 驱动；实测结果是它把窗口**最小化**了，而帧照旧不涨。它的源码里没有「不最小化」的开关。

副作用：窗口化后两个窗口会叠在一起，需要自己摆位；全屏下光标被限制在主显示器内的问题也随之消失。

## 三、`spawn.ini`：席位由段名决定

**`PlayerCount` 不是 spawner 的键**，写进去会被静默忽略。玩家席位来自段名：`[Settings]` 是玩家 0（自己），`[Other1]` 到 `[Other7]` 是玩家 1..7，**段存在即视为人类玩家**。

缺 `[Other1]` 时 `Game::PlayerCount = 1`，`GameMode` 落到 `Skirmish`，于是**根本不调用 `InitNetwork()`**——表现为不等对手、没有对手席位、`[Tunnel]` 整段失效。这就是「加载界面只有一个玩家」的全部原因。

`[Settings]` 与 `[OtherN]` 都至少要给 `Name`、`Side`、`Color`。

### 直连与中继

| 键 | 无 `[Tunnel]`（直连） | 有 `[Tunnel]`（中继） |
|---|---|---|
| `[Settings] Port` | 自己的 UDP 绑定端口 | 自己的隧道 id，且绑定端口被强制为 0 |
| `[Other1] Port` | 对端的真实 UDP 端口 | 对端的隧道 id |
| `[Other1] Ip` | 对端真实 IP | 必须是 `0.0.0.0` |

直连模式最简单，本机只要两边 `Port` 不同（同端口 bind 会失败）。中继模式下 `Tunnel::SendTo` 会给每个包加 4 字节头 `[from][to]` 并全部发给 `[Tunnel] Ip:Port` 这一个地址——它不是直连协议，CnCNet 客户端自己在本地起一个这样的桥。

### `-SPAWN` 不等人

`Spawner::StartGame()` 直接 `LoadSidesStuff()` 后 `StartScenario()`，中间没有等待逻辑；等对手发生在游戏内的连接建立阶段，超时由 `ConnTimeout`（默认 3600 帧，60 fps 下约 60 秒）控制。所以**单实例跑时会在加载界面停约 60 秒然后自己进对局**，这是正常的。

## 四、两个游戏目录

第二个目录用**硬链接**省空间：两份目录的表观体积都是 1.9 GB，但 `.mix` 之类只占一份。

规则是**只链只读资产（`.mix`、`.mmx`、`.yro`、`.exe`、`.dll`），其余一律真副本**。`spawn.ini`、`RA2MD.INI`、`RA2.INI`、`ra2yrcpp.json`、`except.txt` 都是游戏会写的，共享 inode 会让两边互相覆盖——曾经因此把一份**旧崩溃报告**当成新证据，误判了整轮排查方向。

`.exe` 链的是同一个文件，所以 `tools/patch_single_instance.py` 补一次两个目录都生效，还原同理。游戏**不需要**资源出现在工作目录：探针的 `ra2yrcpp.json` 按 CWD 读，而游戏自己的文件按 exe 目录找，所以第二目录必须是一份完整的游戏目录（子目录也不能少，缺了会让 gamemd 早期静默退出）。

两种目录各有自己的 `ra2yrcpp.json`，端口必须不同（本仓用 14521 / 14522）。

## 五、启动与验收

一条命令起整局：

```sh
python3 tools/start_match.py up        # 按名册起全，等到都进对局才返回
python3 tools/start_match.py status    # 逐参与者看进程、端口、阶段、帧
python3 tools/start_match.py down      # 按 PID 停
```

名册在 `config/match.json`：每方一行，给名字、游戏目录、探针端口、`Side`、`Color`。目录与端口是部署事实，故放配置而不是命令行参数。

**起局必须一次起全。** `-SPAWN` 不等对手，游戏自己在加载界面等连接；只起一个实例的后果是它在加载界面干等约 60 秒再判对方掉线——这不是 bug，是名册没起全。同理，**「就绪」的判据只能是每个参与者都进对局**，不能是「进程起来了」：`up` 就是等到最后一方报到 `STAGE_INGAME` 才返回。

**停不能按映像名。** 两个参与者的可执行文件同名，`taskkill /IM` 会一次杀掉两个。`MatchHost.stop()` 按 PID 停，PID 在启动时记下；进程重启后 PID 会丢，那时用 `Win32_Process` 的 `ExecutablePath` 把进程归属回各自的目录——两个目录的启动路径不同，即使可执行文件是同一个硬链接。

验收看四条硬证据，缺一条都不算通：

| 证据 | 手段 |
|---|---|
| 两个进程同时在 | `tasklist` 里出现两个 `gamemd-spawn-ra2yrcpp.exe` |
| 各自绑对了端口 | `Get-NetUDPEndpoint -OwningProcess <pid>`，应为 15000 / 15001 |
| **双向**都有包 | `ra2yrcpp.json` 设 `"trafficFilename": "traffic.pb"`，再用 `tools/read_traffic.py` 解 |
| 帧号同步推进 | 两个探针的 `current_frame` 差值保持在一帧上下 |

判据里最容易被跳过的是第三条。修好之前实测是 `source=0 -> destination=1` 单向 413 个包、另一个方向 **0 个**——只看进程和 `stage` 会误以为已经联上。修好后两边都是双向（例如 610 与 599 个）。

两侧 `state.houses` 里都应出现对方的 `Name`，`is_human_player` 为真而 `current_player` 为假。

## 六、坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 把旧崩溃报告当本次证据 | 整轮排查方向错 | 先看文件时间戳与 inode；硬链接会让两个目录共享同一份 |
| 第二个目录只复制文件、漏掉子目录 | gamemd 启动即静默退出 | 整个目录都要，`Internet`、`SavesDir`、`RMCache` 等子目录不能少 |
| 先起 A、隔十秒再起 B 来「对照」 | 两边结果一样，看着像「本来就不暂停」 | 换顺序重做：**故障跟着启动顺序换人**才说明是互斥 |
| 用 `PlayerCount` 声明对手 | 静默退回单机 Skirmish | 用 `[Other1]` 段 |
| 以为第二个实例崩了 | 白查一轮崩溃 | 干净退出（rc=0、无转储）就是命中了单实例守卫 |
| 只起一个实例就想看对局 | 两边都进不了游戏：一方在加载界面干等约 60 秒后判对方掉线 | 用 `tools/start_match.py up` 按名册起全 |
| 把「进程起来了」当就绪 | 端口还没通就下令，白忙 | 判据是每个参与者都到 `STAGE_INGAME` |
| 两个游戏进程共用一个 `ra2yrcpp.json` | 探针抢同一端口，abort | 各自目录各一份，端口不同 |

## 七、地图上限

`spawnmap.ini` 的 `[Basic]` 写着这张图能坐几个人：`MaxPlayer`、`MinPlayer`、`NumberStartingPoints`。当前这张 "Action Reaction" 是 `MaxPlayer=2`、`NumberStartingPoints=2`，正好两人。席位超过上限会崩，所以要三个以上就得换地图——不是改配置能解决的。
