# 架构设计

目标系统：一个能玩《红色警戒2：尤里的复仇》的 Agent，支持玩家、Agent、游戏内置电脑玩家之间的自由组合对战，并允许玩家在 Agent 决策的各层级介入。

引擎能力与约束见[探针实验结论](../引擎/探针实验结论.md)与[命令能力测绘结果](../引擎/命令能力测绘结果.md)。

## 设计支柱

**Agent 即玩家。** Agent 只能看到其阵营在当前迷雾下可见的信息，不得读取全图状态。观测与决策均须尊重迷雾。引擎侧的迷雾信号见[探针实验结论](../引擎/探针实验结论.md#迷雾)。

**层间交换意图，不交换动作。** 上层写下意图，下层把它拆解为更具体的意图，只有最底层才落到引擎动作。任何一层都不直接调用引擎。

**所有权与租约显式化。** 每个可下达的对象在某时刻归属于某一层。下层可向上请求接管，上层可向下授予或收回，归属变化沿层级传播。

**一切决策留痕。** 每次决策记录来源层、时间、依据与结果，写入同一份决策日志。

## 分层意图栈

只有三层，细则见[技法框架](技法框架.md)。

| 层 | 名称 | 时间尺度 | 决策者 | 产出举例 |
|---|---|---|---|---|
| 2 | 指挥 | 模型自定 | 人 / LLM | 「推进到该矿点」 |
| 1 | 技法 | 每 tick 22–45 帧 | 模型与人离线写的固定代码 | 「移动到该格」 |
| 0 | 基础设施 | 游戏帧 | 固定代码 | 引擎命令 |

**LLM 不接触模拟状态。** 指挥层只写意图数据；技法与基础设施是确定性代码，逐帧的事全在它们手里。这样做的依据是 LLM 调用昂贵且不适合逐帧节奏，且它的弱项恰在微操。

## 人的介入模型

人与模型直接对话，介入因而没有独立通道：人说的话由指挥层翻成意图，与模型自己发的走同一条路。

介入沿三个维度描述：

| 维度 | 取值 |
|---|---|
| 方式 | 观察 / 建议 / 接管 / 授权 |
| 持续 | 一次性 / 临时 / 持久 |
| 对象 | 目标 / 单位 / 技法 / 等级 |

「临时接管这三辆车」即指挥层在此期间不为它们发意图，只执行人给的；到期后恢复。技法与等级的把关同样经对话决定，例如停用某条技法、关掉某一档等级。

## 现在就要留的缝

只固化三件字段级的事，其余实现全部推迟：

1. **意图对象可序列化** —— 意图是数据而非函数调用，便于记录、回放与人工编辑。
2. **意图带来源与 TTL** —— 每条意图标注来源层与有效期，使接管与过期可自动处理。
3. **单一决策日志** —— 所有层的决策写入同一处，便于事后归因。

## 适配层的职责边界

适配层是 L0，只做确定性的翻译与防护，不含任何策略。

**做**：维护与服务端的连接；解析 `GameState`、地图与类型表；按阵营与迷雾过滤观测；把意图翻译成协议命令；发送前校验；归一化错误；维护对象标识的稳定性。

**不做**：选择打谁、造什么、去哪；判断局势；分配单位给任务。这些属于技法与指挥层。

**必须处理的引擎约束**：

| 约束 | 适配层的对策 |
|---|---|
| 排队命令须主循环推进，窗口失焦即停 | 发送后检测帧是否推进，停滞则报错而非静默等待 |
| 失败经 `error_message` 返回，形状不一 | 归一化为统一异常类型 |
| 单帧观测 11.9 KB 且对象全量重发 | 压缩与降采样 |
| `pointer_self` 在变身时改变 | 不以指针作长期标识，跨状态变更后重新解析 |
| 对象处于 `Mission_Construction` 时 `UnitOrder` 拒绝 | 按动作选路 `ClickEvent` 或 `UnitOrder` |
| 地图 304 KB 只能一次取回 | 观测层维护底图，按 `cells_difference` 增量更新 |
| 坐标越界会崩溃游戏 | 发送前本地校验，见[测绘结果](../引擎/命令能力测绘结果.md#校验层) |
| 单位指令不校验归属，任何阵营的对象都能下令 | 校验层默认拒绝非己方对象，越权须显式声明 |
| `MissionClicked` 无条件传格子，比 `UnitOrder` 多一条崩溃路径 | 任务类动作一律走 `UnitOrder` |

## 源码目录

`src/ra2agent/` 按层分包；`constants.py`、`errors.py`、`wake.py` 是跨层管道，留在根。

```
src/ra2agent/
  engine/    与引擎对话的底层：client、payloads、proto、wire、state、identity、
             observation、validate、events
  runtime/   意图与运行时：intents、executor、micro（技法层执行体）、autopilot、formation
  data/      规则数据：rules（解析 rulesmd.ini）、catalogue（可造清单与前提查询）
  deploy/    进程与部署：game（起停与焦点）、winfocus、match（名册与对局宿主）
  tactics/   技法：core、conditions、builtin/、local/
  command.py 指挥层：模型看到的五个工具、事件上报、落点查询
  mcp.py     入口：MCP 服务（DSH 插件按 `ra2agent.mcp` 拉起，路径不可改）
  watch.py   入口：常驻监听（模型空闲期间把事件投成唤醒）
  replay.py  入口：离线回放验证
```

## 依据

- HIMA（[arXiv 2508.06042](https://arxiv.org/abs/2508.06042)）：少量长时程 LLM 调用优于逐帧调用，Lv.6 难度通关率由 25% 提升到 84%；LLM 的弱项在微操。
- Steamhammer（BWAPI）的结构收敛到 Strategy → Operations → Squads → Skills 四层，与本设计的分层同构。

## 暂不纳入

- 强化学习训练
- 多模态视觉输入
- 通用游戏 AI 框架

## 已定的接缝

### L1 与 L0 的边界

判据：**L0 从不选择，L1 是最低的会选择的层。** L0 只回答「这个意图能不能执行」，L1 回答「这一步该做什么」。

| 行为 | 层 | 理由 |
|---|---|---|
| `Move(unit, cell)` 翻译成 `UnitOrder{MOVE}` | 基础设施 | 无条件翻译 |
| 检查坐标是否在地图内 | 基础设施 | 校验，不选择 |
| 对象处于 `Mission_Construction` 时改走 `ClickEvent` | 基础设施 | 选路规则固定，无策略 |
| 等待命令生效、归一化未知结果 | 基础设施 | 验证与报告，不选择重试策略 |
| 「走到 A 点，途中遇敌就停下反击」 | 技法 | 条件分支 |
| 「卡住超过 N 帧就换路点」 | 技法 | 条件分支 |
| 队形展开成哪几个格 | 技法 | 计算且带策略性 |
| 「哪三个单位归这支队」 | 指挥 | 资源分配 |

**技法层按 2–5 Hz 运行，不逐帧。** 引擎自行处理寻路与自动开火，逐帧微操无收益；逐帧的事全部归基础设施。指挥层的节奏自定，不必与技法层同拍。

**技法用普通 Python 函数写，由模型管理，不引入 DSL。** 技法的产出仍是意图，只是更具体，使各层接口同构。

基础设施的命令选路与生效判据见 [`src/ra2agent/runtime/executor.py`](../../../src/ra2agent/runtime/executor.py) 的模块文档；技法的形态与接口见[技法框架](技法框架.md)。

### 意图 schema

信封字段：

| 字段 | 含义 |
|---|---|
| `id` | 唯一标识 |
| `parent` | 父意图 id，构成溯源链 |
| `layer` | 发出层 |
| `issuer` | 人、模型或脚本的标识 |
| `kind` | 意图类型，用于反序列化 |
| `scope` | 涉及的对象或区域，所有权判定的依据 |
| `created_frame` | 发出时的游戏帧 |
| `ttl_frames` | 有效期；`None` 表示直到显式撤销 |
| `state` | `active` / `satisfied` / `failed` / `expired` / `superseded` |

载荷分两类：技法到基础设施用类型化子类加注册表（`kind` 到类），保留类型约束；指挥到技法用通用载荷 `TacticCall{tactic, params}`，使模型加新技法不必改 schema。

四条已定的语义：

| 项 | 决定 | 理由 |
|---|---|---|
| 意图是一次性命令还是持久目标 | **持久目标** | 有 TTL 与租约才讲得通；人的「接管」本质是撤掉 Agent 的持久目标、换上自己的 |
| TTL 的单位 | **游戏帧** | 引擎时钟是帧；失焦时帧不推进，恰好符合「游戏时间」语义。人类口述的秒数在发出时换算 |
| 意图引用的对象 | **Agent 侧稳定 id** | `pointer_self` 在变身时改变；L0 维护 id 与引擎指针的映射，每次观测重新解析 |
| 意图状态由谁更新 | **消费它的下层** | 技法报告已到位，指挥层报告目标已达成；发出层只负责创建与撤销 |

**决策日志**为 JSONL，一局一个文件，**以游戏帧为主键**。只记决策与命令结果，不记观测——单帧 11.9 KB 无法逐帧留存，且可经录制文件复现。每条决策附其依据的事实摘要，使归因不必翻原始状态。

### 人机组合对战

ra2yrcpp 是「单进程、单当前玩家」的接口：`add_event` 以 `HouseClass::CurrentPlayer` 归属事件，`ProduceOrder` 取 `current_player()`。

分两阶段：

| 阶段 | 形态 | 能验证什么 | 障碍 |
|---|---|---|---|
| 一 | 单进程同席位，人与 Agent 共控一个玩家 | 人的介入模型 | 共享视野，验证不了迷雾隔离 |
| 二 | 双进程局域网对战 | 完整的自由组合对战；每个进程天然只有己方迷雾 | 多人局须 `PlayerCount≥2` 并等待对端，`-SPAWN` 单跑会挂起；CnCNet 的多人协作协议需另行研究 |

**要验证迷雾隔离就必须有独立进程**，这是阶段二的硬理由。

**席位识别**：以 `House.current_player` 判定己方，并断言恰好有一个；为 0 或大于 1 时报错退出，不做猜测。

## 待验证

- `AddEvent` 的 `spoof=true` 会改用 `ev.house_index()` 归属事件而非当前玩家。若该路径可靠，单进程内即可为其它阵营下达生产指令，阶段二可省。
