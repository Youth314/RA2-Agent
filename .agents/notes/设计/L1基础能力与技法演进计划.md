# L1 基础能力与技法演进计划

更新日期：2026-10-02。状态：已接受的建设方向与实施计划；S1 已完成静态审计与契约草案，并落实现有 Move / Stop 执行安全的首轮离线实现；S2 首轮限定人工操作测绘已收尾，未测边界明确保留；S3 已接入只读原版事件输入及 Guard 首版受控接口，相关离线与编译通过，限定真机结果见[Guard 验证](../验证/Guard接口验证.md)，Grizzly 与 CMIN / Engineer-FV 正例和 12 个服务端拒绝场景通过；首组 Guard 限定验收收尾，准备对应 S4，其他能力与正式技法迁移尚未完成。

## 1. 目标与已确认决策

以真实玩家能使用的操作作为基础能力基准，补齐底层与游戏交互的引擎。原版行为、单位差异、当前支持情况与证据统一见[玩家操作能力表](../引擎/玩家操作能力表.md)；候选项目的复用边界见[引擎接口复用评估](../引擎/引擎接口复用评估.md)，本计划不复制其能力清单。

模型的游戏动作只通过技法下达。先建设 L1 可使用的完整受控基础接口，不要求每项基础能力立即成为公开技法。基础玩家操作可以按需要封装为薄技法，组合技法可以复用它们或直接构造同一基础意图。模型侧的暴露方式可逐步比较，不锁定单一方案。

工具数量与选择成本分别处理。现有 status/tactics/call/cancel/game 五个工具保持作为起点；即使工具数固定，技法目录、参数说明和相似行为也可能增加选择成本。需要管理模型实际看到的卡片和说明，而非只计工具数量。

## 2. 分层与调用边界

| 层次 | 职责 | 对外形态 |
|---|---|---|
| L0 基础设施 | 原版操作翻译、归属/可见性/目标校验、游戏线程执行、状态回读、错误与回执 | L1 可消费的类型化意图及结果契约 |
| L1 基础能力使用 | 表达明确操作与目标，处理任务状态；需要时提供薄技法 | 意图构造零件，或内部/公开技法 |
| L1 组合技法 | 目标选择、队形、分支、恢复、持续任务和结束条件 | 可复用的确定性技法 |
| L2 指挥 | 选择技法、给参数、管理任务和复盘 | 现有五个工具 |

“L1 可用接口”不是允许技法直接连接 DLL、调用 engine client 或任意写内存。继续遵循层间交换意图、L0 执行引擎动作的边界。构造意图不做 I/O，发送前在 L0 重查对象身份、归属、状态与合法性。

原版指令内含的寻路、自动接敌、警戒、采矿往返和维修由游戏执行；它们属于玩家指令的既有语义。L0 不新增战略目标选择。L1 可按任务需要选择目标，但不能读取隐藏敌方对象作为点名目标。

基础意图构造零件不必注册成技法。需要让模型调用某操作时，增加共享同一基础能力的薄封装。组合技法调用其他技法仍经过既有 ctx.call 门控；直接构造基础意图也必须经过统一校验、租约、日志和等级约束，不能形成绕过路径。

## 3. 基础能力契约先行

| 项目 | 必须表达的内容 |
|---|---|
| 请求身份 | 局次、请求 ID、来源、父意图、依据帧、有效期 |
| 操作与目标 | 玩家语义、稳定单位 ID、地点/对象/路径等目标类别，以及明确的强制修饰 |
| 适用性 | 静态类型、运动域、武器与动态乘员/部署状态、目标类别；混合单位逐单位返回理由 |
| 执行回执 | 请求受理、实际下令、操作生效和任务目标完成分开记录；无法确认时明确说明 |
| 生命周期 | 一次下令与长期维持的差异、TTL、重发条件、替换、租约交还和自动层接管政策 |
| 对象变化 | 装载、驻军、消耗、变身、离图与死亡分别归因 |
| 路径与计划 | 节点动作、循环、提交、取消；append 仅对已验证的原版能力开放 |

已有意图主要表达持久目标。Guard 首版一次输入结算已落实并更新[架构设计](架构设计.md)，适用范围与验证见[Guard 接口验证](../验证/Guard接口验证.md)；现有运行时已补充观测回执与未知结果表达，实施范围与限制见[Move / Stop 接口离线验证](../验证/MoveStop接口离线验证.md)；完整新结果契约尚未实现。

基础命令生效后可以结束 Agent 任务，但游戏行为可能继续；释放租约之后也可能被自动层覆盖。不能默认所有基础操作每拍重发，也不能把 cancel 任务直接解释为 Stop 单位。是否提供“取消并停止”的显式组合行为、何时恢复自动经济，均需明确设计。

## 4. 模型可见面的组合策略

| 策略 | 使用方式 | 约束 |
|---|---|---|
| 常用能力常驻 | 默认展示经验证的常用组合技法与少量基础技法 | 常驻集合依据实际使用调整，不预设最优数量 |
| 按需发现 | tactics 按目标/用途发现其他能力，再返回完整参数 | 不必添加第六个工具；当前查询只支持名称/说明子串，语义检索尚未实现 |
| 动态适用过滤 | 按合法观测中的类型与动态状态筛选 | 明确不可用可过滤；战术价值低优先降序，保留可解释查询途径 |
| 分类与分级说明 | 先给简短用途，再按需展开参数、约束和示例 | 指挥层仍只调用被允许的技法，不借发现公开内部引擎入口 |
| 合并接近的变体 | 对语义相近、参数一致的行为提供明确模式 | 不做包含大量无关分支的万能操作，避免仅把选择成本移入参数 |
| 可调整组合技法 | 护送维修、推进、侦察、经济管理等常见任务暴露目标和结束条件 | 使用受控基础能力，不让每个组合技法重复实现原版行为 |

expose=False 表示模型不能调用，不只是默认列表不展示。按需可发现的公开能力与仅供 L1 使用的零件应分开表达；不能把所有不常用操作都设 expose=False 后声称模型还能搜索调用。

动态过滤需要在具体 subject/target 下重查条件。目录可见不代表受理成功；受理时和实际发送时仍需校验，避免观察与执行之间状态变化。

基础设施与模型可见策略分开版本化，使同一组底层能力可以比较“组合技法优先”“按需基础技法”“不同目录展示”等方案。初期先使用组合技法和少量必要基础技法，保留按需扩展入口。

工业实践参考：[按需工具发现](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)、[工具职责与描述设计](https://www.anthropic.com/engineering/writing-tools-for-agents)。这些提供设计参考，不证明同样策略已在本项目产生收益。

## 5. 每局反馈与技法迭代

每局记录接口版本、技法库指纹、模型可见目录/策略、调用与参数、拒绝原因、重试、接管与覆盖、执行回执和结算。沿用决策日志中的局次与游戏帧，附合法观测的事实摘要；需要新增的字段在实施阶段定义，避免重复存储无用全量状态。

复盘让模型提出：想做但没有能力的任务、反复调用/手动补救的任务、名称或参数歧义、预期与实际行为差异，以及反复出现而值得组合的操作序列。每条建议必须关联实际请求和执行证据。

| 归因 | 优先处理 |
|---|---|
| 原版能力无法下达或回读 | 补接口、观测或执行判据 |
| 技法组织与恢复错误 | 改组合逻辑、参数、生命周期 |
| 有能力但找不到/分不清 | 改目录、描述、分类和按需发现 |
| 能力正常，决策目标不合理 | 调整指挥策略，不无条件新增技法 |
| 原版规则或局面导致操作不可用 | 正确拒绝并解释，避免误记为引擎缺陷 |

迭代流程：提出建议 → 核对日志 → 选择有证据的改动 → 离线验证 → 受控真机验证 → 版本化启用 → 后续对局比较。默认局间调整，保持一局内能力版本可追溯；不因一局输赢自动修改代码并启用。

比较指标包括任务完成情况、无效/重复调用、参数与受理错误、模型选择耗时、命令生效耗时、上下文与调用成本。胜率作长期指标，尽量固定场景、对手与初始条件并重复比较，避免把偶然结果归因于目录策略。

## 7. 后续任务分工原则

源码调查、测试矩阵设计、互相独立的离线测试和日志分析可拆成独立任务。涉及同一游戏进程、连接、窗口焦点、单位和日志消费游标的真机任务必须由一个执行者统一控制，避免并发命令改变实验条件。

独立游戏实例仅在端口、存档、日志、连接及焦点推进条件都隔离后才考虑并行；两个实例互相联机是一个联合实验，不能假定它们是独立资源。离线回放只验证固定观测下的意图、校验与结算，不证明新原版命令的实际效果。

委派任务必须写清场景、文件范围、允许动作、初始状态、步骤、判据、超时与清理、证据输出位置和禁止并发使用的资源。主 agent 汇总和核对结果，测试结论区分通过、失败、未执行和无法确认。

## 测试投入原则

采用[能力验证方法](../验证/能力验证方法.md)中的最小充分验证。阶段与矩阵用于定位未知，不要求建立完整工程流水线，不以无头化为前置条件；用户操作、观察或录屏能够明显缩短准备时间时，应提供明确步骤并请用户协助。只对重复成本高、失败影响大或需要长期回归的场景逐步增加自动化。
