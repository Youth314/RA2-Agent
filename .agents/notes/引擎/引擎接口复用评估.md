# 引擎接口复用评估

研究日期：2026-10-01。依据为候选仓库的当前源码、上游明确列出的验证限制和本项目现有实现；此次未构建候选项目、未运行游戏或完成兼容性验证。研究基线见[相似项目调研](../../drafts/研究/相似项目调研.md)，本项目实机问题见[对局实测缺陷清单](../../drafts/问题/对局实测-技法层缺陷清单.md)。

## 结论

在此次候选范围内，没有发现可直接替换 ra2yrcpp、同时覆盖原版 YR 状态、生产、单位命令和双实例联机的成熟接口。最可行的路线是保留 ra2yrcpp 的通信与录制骨架，先修本项目误判，再从 YRpp 与 LuaAPI 提取小范围原版引擎实现，逐项验证后补入引擎侧。无需为了这些补充改成 OpenRA 或网页引擎。

能够近期落地的借鉴是：统一生产完成判据、攻击目标与坐标同时传递的对照实验、冻结最后可见敌情、命令回执与任务完成分开表达。需要修改 DLL 的候选是：直接采矿任务、目标/矿车存量/超武状态等观测、SpecialPlace 事件载荷与修理路径。LuaAPI 提供有价值的源码语义，但其生产接口已被上游标为 Blocked，双人联机未验证，不能整体替换。

## 1. 优先使用现有协议修本项目

### 1.1 待放置判据已经有足够数据

ra2yrcpp 已返回 `Factory.object`、`owner`、`progress_timer`、`on_hold` 与 `completed`；其中 `completed` 由 `progress_timer == PRODUCTION_STEPS` 计算。本项目也已解析这些字段。`has_pending_building()` 仍只检查己方对象 `in_limbo`，事件检测也按进入 limbo 判定，因而开工即可触发待放置，而非完工才触发。这是 Python 使用语义问题，不需要下载另一个游戏接口。

建议定义一个共享查询：从己方工厂找到已完成、产出对象存在且为建筑、仍在 limbo 的条目，条件门、status、放置技法和事件检测共同调用。必须明确受理、生产完成、建筑落地三个时刻。不要为读取完成状态调用 YRpp 的 `CompletedProduction()`；其注释表明它会检查并更新工厂状态，不能当作纯观测函数。

源码依据：[ra2yrcpp/src/ra2/state_parser.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/ra2/state_parser.cpp#L582)；[yrpp/FactoryClass.h](https://github.com/Ares-Developers/YRpp/blob/61d0887eb6040cfb36af16d592e9770ceae4dfb2/FactoryClass.h#L61)。本项目位置：[conditions.py](../../../src/ra2agent/tactics/conditions.py:101)、[events.py](../../../src/ra2agent/engine/events.py:238)、[state.py](../../../src/ra2agent/engine/state.py:137)。

### 1.2 攻击指针错误存在可隔离的缓存路径

`UnitOrderCtx::click_mission()` 在 `target_object != 0` 且没有 `coordinates` 时调用 `get_object_entry(target)` 取坐标；该函数从服务端状态缓存查找对象，失败即抛出 `object N not found`。缓存包含 `TechnoClass::Array` 中的各方对象，源码没有在此处只保留己方的筛选，因此不能将现象直接定性为“不允许攻击敌方对象”。

本项目 `_plan_attack()` 只传目标指针；pyra2yr 的 `attack()` 也是同样封装，没有解决这个问题。可做同一目标的两组对照：仅指针、指针加当前可见坐标。第二组可避开服务端的坐标缓存查找，但仍把目标指针交给引擎，不能保证对象生命周期安全或命令生效。需要覆盖静止敌兵、敌建筑、矿车采矿与卸货，并记录观测帧、执行帧、目标存活状态和命令结果。

不能自动把不可见目标的历史指针补进命令；丢失目标时应由技法决定继续追踪最后可见位置还是结束。对于矿车进厂等短暂 limbo，需区分“当前不可指挥/不可攻击”和“已死亡”。

源码依据：[ra2yrcpp/src/commands_game.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/commands_game.cpp#L81)；[ra2yrcpp/src/ra2/state_context.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/ra2/state_context.cpp#L120)；[ra2yrcpp/src/ra2/state_parser.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/ra2/state_parser.cpp#L648)；[pyra2yr/pyra2yr/manager.py](https://github.com/shmocz/pyra2yr/blob/05a20df628eff3cb28d9530e80addcca57a2cb0c/pyra2yr/manager.py#L269)。本项目位置：[executor.py](../../../src/ra2agent/runtime/executor.py:394)。

### 1.3 集火提前结束与接口失败是两个问题

本项目缺陷记录中的“追到建筑后 satisfied、没有发 Attack”发生在技法与运行时结算。新增引擎能力不能修复这类提前结束。建议明确任务的阶段：追近、攻击命令已生效、目标完成条件；移动到位只能完成追近阶段。攻击命令生效也不能与目标摧毁等同。现有执行器只检查攻击单位 `mission == ATTACK`，可作为受理效果信号，不能证明正在攻击指定对象或造成伤害。

## 2. 从 LuaAPI 借鉴原版任务调用

### 2.1 明确采矿任务，避免用移动冒充采矿

LuaAPI 的 `HarvestAt()` 查目标格后，设置 `FootClass::Destination` 并排入 `Mission::Harvest`；`MoveTo()` 则排入 `Mission::Move`。这提供了补充专门采矿动作的实现线索，正对应本项目将矿车移动到矿格后等待原版 AI 接手的局限。

但 LuaAPI 的 API 审计把 `HarvestAt` 与 `GetHarvestLocation` 标为 Unverified、无现有消费者。因此只能认为源码路径存在，不能声称已验证有效。单机实验须检查采矿、装满、返厂、卸货与恢复采矿的完整循环；双实例实验还须检查事件是否同步。直接修改一侧的 Destination/任务不应直接用于联机。

源码依据：[luaapi/src/bindings_techno.cpp](https://github.com/WolfCTOS/LuaAPI-for-Red-Alert-2/blob/989ee3828385916211805426a532a0dea8336061/src/bindings_techno.cpp#L633)；[luaapi/PROJECT/API_FREEZE_AUDIT.md](https://github.com/WolfCTOS/LuaAPI-for-Red-Alert-2/blob/989ee3828385916211805426a532a0dea8336061/PROJECT/API_FREEZE_AUDIT.md#L65)。

### 2.2 攻击与停止可用作语义对照

LuaAPI `Attack()` 调用 `SetTarget(target)` 后排入 `Mission::Attack`；`Stop()` 清除 Target 与 Destination 再排入 Stop。可借此检查 ra2yrcpp 的 ClickedMission 路径是否确实设置期望目标，以及为什么 mission 已变但未输出。更稳妥的近期改进是新增目标回读字段，让运行时验证当前目标，而非立即改为内存赋值控制。

这些直接任务调用没有自动获得原版联机同步保证。LuaAPI 也明确双人客户端未验证、没有永久 order lease；因此只适合作为隔离实验或未来同步命令实现的参考。

源码依据：[luaapi/src/bindings_techno.cpp](https://github.com/WolfCTOS/LuaAPI-for-Red-Alert-2/blob/989ee3828385916211805426a532a0dea8336061/src/bindings_techno.cpp#L713)；[luaapi/README.md](https://github.com/WolfCTOS/LuaAPI-for-Red-Alert-2/blob/989ee3828385916211805426a532a0dea8336061/README.md)。

### 2.3 指针安全实现不能原样照搬

LuaAPI 的 `ValidateTechno()` 会直接调用裸指针的 `WhatAmI()` 并读取 Health；`CheckTechno()` 主要检查 userdata 类型和空指针。部分命令用 SEH 包住修改，但前置校验本身并非完整的对象存活证明。它也没有把所有访问统一改成 ID 查找。不能因为 README 声称安全，就将这套代码直接移入 ra2yrcpp。

更合适的设计是每次执行在游戏线程按当前对象集合重新解析对象，结合 UniqueID、局次标识与对象类型核验，拒绝跨局旧引用。引擎 UniqueID 可辅助检测指针复用；部署等变身是否延续身份仍由本项目 IdentityTable 处理。游戏线程访问、异常记录与小范围失败隔离可以借鉴，不能用 SEH 代替正确对象生命周期管理。

源码依据：[luaapi/src/bindings_techno.cpp](https://github.com/WolfCTOS/LuaAPI-for-Red-Alert-2/blob/989ee3828385916211805426a532a0dea8336061/src/bindings_techno.cpp#L40)；[yrpp-ra2yrcpp/AbstractClass.h](https://github.com/shmocz/YRpp/blob/173447cf75f5175e5c6530a439fbadc106ea6a6f/AbstractClass.h#L163)。

### 2.4 生产接口不能复用为成熟实现

LuaAPI `AI.QueueUnit` 遍历己方工厂并调用 `DemandProduction`，但上游审计明确记载接受请求后没有可归因的产出，状态为 Blocked。其 `CountUnit` 统计工厂队列，不等于己方地图上单位总数。本项目已能经 ProduceOrder 和原版生产事件下单，应继续使用现有链路。

源码依据：[luaapi/src/bindings_production.cpp](https://github.com/WolfCTOS/LuaAPI-for-Red-Alert-2/blob/989ee3828385916211805426a532a0dea8336061/src/bindings_production.cpp#L37)；[luaapi/PROJECT/API_FREEZE_AUDIT.md](https://github.com/WolfCTOS/LuaAPI-for-Red-Alert-2/blob/989ee3828385916211805426a532a0dea8336061/PROJECT/API_FREEZE_AUDIT.md#L65)。

## 3. 从 YRpp 补足观测与事件

### 3.1 SpySatActive 是研究入口，不能直接解除可见性过滤

YRpp 明确包含 `HouseClass::SpySatActive`；ra2yrcpp 的 House 解析没有导出它。建议先添加只读诊断并在建筑建造、通电、断电、被毁前后与人类画面对照，再确认它与逐格 shroud、敌对象可见性之间的关系。不能仅因该位为 true 就把原始全量对象全部交给模型，仍需处理隐形、伪装、潜水及特殊不可见对象。

源码依据：[yrpp-ra2yrcpp/HouseClass.h](https://github.com/shmocz/YRpp/blob/173447cf75f5175e5c6530a439fbadc106ea6a6f/HouseClass.h#L972)；[ra2yrcpp/src/ra2/state_parser.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/ra2/state_parser.cpp#L561)。Trainer 的 Reveal 操作是主动改地图状态，不能拿来修复公平观测：[trainer/src/backend/hook/trainer.cc](https://github.com/AdjWang/RA2YurisRevengeTrainer/blob/352795c71a7abca55f7d04e849c1f9844411c8c8/src/backend/hook/trainer.cc#L883)。

### 3.2 超武路径在原版存在，但当前接口没有接完整

YRpp 暴露 `HouseClass::Supers`、`SuperClass::Granted`、`IsCharged`、`IsOnHold`、`RechargeTimer` 及 `CanFire()`、`Launch()`。专用 YRpp 还提供 SpecialPlace 事件构造；ra2yrproto 已定义 SpecialPlace 的 id/location 载荷和事件号。

然而 ra2yrcpp `StateContext::add_event()` 只填充 production、place、sell_cell、sell、deploy，没有 SpecialPlace 分支；EventParser 也没有解读该载荷。本项目 payloads 同样未提供。因此“协议有字段”不能推出“Python 传入就能生效”。需要补 DLL 的事件载荷和只读超武观测，随后才有条件写伞兵或超武技法。

联机候选应优先沿原版事件队列发令，核对超武实例索引而非猜测类型索引，验证坐标单位、充能、归属、单次消耗与两侧一致性。不能采用 Trainer 直接改 IsCharged 的做法。CnCNet spawner 证明仍存在 OutList 事件路径，但不同 YRpp 分支的类型布局必须按锁定依赖核对。

源码依据：[yrpp/SuperClass.h](https://github.com/Ares-Developers/YRpp/blob/61d0887eb6040cfb36af16d592e9770ceae4dfb2/SuperClass.h#L56)；[yrpp-ra2yrcpp/EventClass.h](https://github.com/shmocz/YRpp/blob/173447cf75f5175e5c6530a439fbadc106ea6a6f/EventClass.h#L285)；[ra2yrproto/ra2yrproto/ra2yr.proto](https://github.com/shmocz/ra2yrproto/blob/0ad72455bcdcf5626d0e17c3311ea82556da2ad3/ra2yrproto/ra2yr.proto#L504)；[ra2yrcpp/src/ra2/state_context.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/ra2/state_context.cpp#L38)；[ra2yrcpp/src/ra2/state_parser.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/ra2/state_parser.cpp#L318)；[yrpp-spawner/src/Ext/Event/Body.cpp](https://github.com/CnCNet/yrpp-spawner/blob/d65600eeb77dc9401999d90a29f950d1f63f374d/src/Ext/Event/Body.cpp#L26)。

### 3.3 修理必须区分动作种类

ra2yrcpp 的 UnitAction.REPAIR 映射到 Mission_Capture；pyra2yr 的真机测试使用 Engineer 对己方受损建筑下这条命令并等待满血，这与工程师进入建筑的语义相关。不能将它认作工具栏修理，也不能仅凭名称判定所有修理都不可用。

建议分别测绘 Engineer 修理/占领、维修厂修理、工具栏建筑修理。原版事件枚举有 Repair，专用 YRpp 有目标类事件构造，但当前通用 add_event 未填充其独立载荷；其正确事件类型、TargetClass 编码和作用对象必须逐一核验，不能只把 Mission_Capture 改成 Mission_Repair。

源码依据：[ra2yrcpp/src/commands_game.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/commands_game.cpp#L81)；[pyra2yr/pyra2yr/tests/test_complex.py](https://github.com/shmocz/pyra2yr/blob/05a20df628eff3cb28d9530e80addcca57a2cb0c/pyra2yr/tests/test_complex.py#L90)；[yrpp-ra2yrcpp/EventClass.h](https://github.com/shmocz/YRpp/blob/173447cf75f5175e5c6530a439fbadc106ea6a6f/EventClass.h#L285)。本项目[命令接口源码结论](命令接口源码结论.md)中的修理限制在开展实验时需要按动作种类细化。

### 3.4 可增加的观测字段

优先读取当前攻击 Target、Destination 的对象类型与坐标、TechnoClass 的 Ammo/Tiberium 存量、矿车当前 Mission、Factory 的生产状态、己方超武充能和 SpySatActive。这些信息直接服务于“真正开火了吗”“矿车为何没收入”“生产是否完成”的判断。上游当前 Foot 解析只在 Destination 为 Cell 时填坐标，目标为建筑等情况缺少表达；Techno 解析也未提供上述目标和存量。

字段必须先确认目标二进制布局，使用新 protobuf 字段号，并同步维护服务端与本项目解析器；不复用旧号。字段应有“未提供/不可观测/有效值”的区分，避免旧 DLL 的默认值被当成真实 0。只向模型输出己方与合法可见对象的信息。

源码依据：[yrpp-ra2yrcpp/TechnoClass.h](https://github.com/shmocz/YRpp/blob/173447cf75f5175e5c6530a439fbadc106ea6a6f/TechnoClass.h#L648)；[ra2yrcpp/src/ra2/state_parser.cpp](https://github.com/shmocz/ra2yrcpp/blob/ee215f5a01f709c52b1fe4dd333d16cbe5d5f146/src/ra2/state_parser.cpp#L73)。

## 4. 从 Agent 项目借鉴独立设计

### 4.1 dsh-red-alert：冻结最后可见敌情

`FogSafeProjector` 只读取当前可见敌人，将联系人快照保存到 lastSeen；目标隐藏后仅复制冻结的坐标、血量、observedAtTick，不再次读取隐藏对象。可在本项目 Observer 后加入类似记忆，status 展示历史敌建筑、最后观察帧及已探索比例。记忆与当前可见敌人分别标识；隐藏目标的死亡不能从全量底层状态偷偷清除历史记录。

当前本项目对 FogOfWar=Yes 的精确可见性仍有限制；加入 last-seen 不能解决这个限制，也不能作为启用灰雾配置的依据。必须先取得正确的当前视野信号。

源码依据：[dsh-red-alert/packages/game-host/src/fog-safe-observation.ts](https://github.com/vibeinging/dsh-red-alert/blob/10f9041aa5460838c09c21fd22d40192bb8b5cfb/packages/game-host/src/fog-safe-observation.ts#L105)；本项目[observation.py](../../../src/ra2agent/engine/observation.py:142)。

### 4.2 dsh-red-alert：请求身份、回执去重与任务结果分开

其 BrowserCommandTransport 以 requestId/sessionId/matchId/seat 校验回执，拒绝旧 tick，检查重复回执内容，并先持久化结果再交给调用方。可借鉴到本项目唤醒和命令日志：事件带局次、玩家、源帧与对象身份；桥端按稳定事件 ID 去重；明确受理、命令生效、任务达成。

不要直接复用整套浏览器文件传输或导入 TypeScript/Zod/DSH 运行时。原版游戏与本项目都有自己的通信路径，宜只移植契约。单纯携带新状态也不代表作战任务已完成；call 仍需保持快速返回，持续任务由 status 报告。

源码依据：[dsh-red-alert/src/browser-command-transport.ts](https://github.com/vibeinging/dsh-red-alert/blob/10f9041aa5460838c09c21fd22d40192bb8b5cfb/src/browser-command-transport.ts#L427)；[dsh-red-alert/src/command-view.ts](https://github.com/vibeinging/dsh-red-alert/blob/10f9041aa5460838c09c21fd22d40192bb8b5cfb/src/command-view.ts#L35)。赛后 episode 的候选经验和模型采用/拒绝流程也可参考，但应在执行判据可信后再开展：[dsh-red-alert/src/strategy-learning.ts](https://github.com/vibeinging/dsh-red-alert/blob/10f9041aa5460838c09c21fd22d40192bb8b5cfb/src/strategy-learning.ts#L187)。

### 4.3 OpenRA-RL：观测 schema 与当前调用形态

protobuf 明确区分经济、己方单位、可见敌建筑、生产、explored_percent、终局和 interrupt_reason。可借鉴信息组织与评估记录，避免将错误执行回报当成有效策略样本。

当前 BridgeClient 主路径是同步 unary RPC：GetState、FastAdvance、CreateSession/DestroySession，并明确不使用 streaming；不能依据旧概述把它作为成熟的双向推送方案。FastAdvance 依赖它能控制 OpenRA 模拟 tick，本项目真实联机主循环不具备同样控制条件，不能直接照搬。

源码依据：[openra-rl/proto/rl_bridge.proto](https://github.com/yxc20089/OpenRA-RL/blob/5dadd449c912ac2d4021cc8ed84fc0b385b1543c/proto/rl_bridge.proto#L30)；[openra-rl/openra_env/server/bridge_client.py](https://github.com/yxc20089/OpenRA-RL/blob/5dadd449c912ac2d4021cc8ed84fc0b385b1543c/openra_env/server/bridge_client.py#L23)。

## 5. 其余原版相关候选的边界

Trainer 可参考网络线程收到消息后排队、游戏线程执行操作的分工，以及 Steam 运行与崩溃诊断经验。当前 Server::Update 在游戏线程执行任务，网络线程不直接进行这些游戏修改。它的开图、瞬造、充能、加钱操作改变规则状态，不能直接成为本项目控制接口。加入第二套注入与网络服务也会增加 hook 冲突和连接生命周期复杂度。

RA2YR_ReSource 的 FactoryClass 文件仍包含空实现，编译成功不能推出生产或游戏逻辑完成。其影子执行用于比较逆向函数与原始函数，适合处理未知偏移/调用语义，但需要专门的隔离实验，不应整体加载其替代引擎或 TCP 调试服务。YRpp4ida 只作符号和类型辅助。

CnCNet yrpp-spawner 是新的 DLL spawner，当前 ra2yrcpp 使用其自身适配链路，不能不经验证替换。它的 RA2Mode、兼容修复、事件校验和启动源码可用于定位问题，采用补丁时须检查规则改动、目标 exe、hook 地址和事件协议。

源码依据：[trainer/src/protocol/server.cc](https://github.com/AdjWang/RA2YurisRevengeTrainer/blob/352795c71a7abca55f7d04e849c1f9844411c8c8/src/protocol/server.cc#L88)；[trainer/src/backend/hook/game_loop.cc](https://github.com/AdjWang/RA2YurisRevengeTrainer/blob/352795c71a7abca55f7d04e849c1f9844411c8c8/src/backend/hook/game_loop.cc#L91)；[resource/src/system/factory.cpp](https://github.com/Ritanlisa/RA2YR_ReSource/blob/b01d3cf93db69aca9b5cb5054ba04e4358963828/src/system/factory.cpp#L6)；[resource/README.md](https://github.com/Ritanlisa/RA2YR_ReSource/blob/b01d3cf93db69aca9b5cb5054ba04e4358963828/README.md#L89)；[yrpp-spawner README](https://github.com/CnCNet/yrpp-spawner)。其余网页、Mod、评测仓库的用途仍见[相似项目调研](../../drafts/研究/相似项目调研.md)，本调查未对这些次要项目做源码审计。

## 7. 建议实施顺序与验收

| 顺序 | 具体工作 | 所在层 | 验收关注点 |
|---|---|---|---|
| 1 | 统一工厂完成、待放置与事件判据 | Python | 开工不报完工；暂停不误报；完工后只报一次；落地后消失 |
| 2 | 修复 focus_fire 阶段结算，并做目标指针+坐标对照 | Python + 真机实验 | 确实发 Attack；当前目标一致；记录目标掉血；移动目标与 limbo 可解释 |
| 3 | 冻结历史敌情、探索信息、运行任务进度与停滞原因 | Python | 隐藏后数据不更新；有观察帧；跨局清空；移动卡住可读 |
| 4 | 维护一份 ra2yrcpp 补丁基底与可重复构建记录 | 引擎构建 | 记录 DLL/EXE hash、上游和依赖提交、目标架构及补丁；现有命令保持可用 |
| 5 | 增加目标、矿车存量、SpySatActive 和己方超武观测 | DLL + 协议 + Python | 与人类画面、生命周期、断电和临时不可见状态对照；旧 DLL 明确报能力缺失 |
| 6 | 采矿与 SpecialPlace/修理的小范围事件实现 | DLL + 协议 + 技法 | 单机全生命周期有效；双实例不分歧；归属和范围校验；不更改充能/资源规则 |
| 7 | 可信回执之上的重复对局与赛后经验 | 日志与评估 | 终局、任务结果、命令失败可区分；同配置跨对手重复评估 |
